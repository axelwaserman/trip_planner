Phase 4.8 is a cleanup and hardening phase with three parallel tracks: additive Pydantic validators, test fixture centralization, and dead-component deletion. No new dependencies are required. All three tracks are purely additive or subtractive changes to existing files — no architectural changes, no new modules in production code, and no breaking changes to the API surface.

Deletion is safe, and `tsc --noEmit` passes cleanly on the current codebase.

**Primary recommendation:** Implement in three atomic waves: (1) validators + tests for validators, (2) extract fixtures and refactor existing tests to consume them, (3) delete orphan files and verify `tsc --noEmit`.

### Pattern 1: Cross-Field Model Validator (`@model_validator(mode="after")`)

**What:** Runs after all field validators have passed; receives the fully-constructed model instance as `self`; returns `Self` on success or raises `ValueError` on failure.
**When to use:** When validation depends on comparing two or more fields on the same model.

**Example (canonical — from existing `validate_dates` in `models.py`):**

```python
# Source: backend/app/models.py lines 60-72 [VERIFIED: codebase read]
@model_validator(mode="after")
def validate_dates(self) -> Self:
    """Validate return date is after departure date."""
    if self.return_date and self.return_date <= self.departure_date:
        raise ValueError("Return date must be after departure date")
    return self
```

**New validators follow this identical pattern:**

```python
# New validator for FlightQuery (origin != destination)
@model_validator(mode="after")
def validate_origin_destination(self) -> Self:
    """Validate origin and destination are different airports."""
    if self.origin == self.destination:
        raise ValueError("Origin and destination must be different airports")
    return self

# New validator for FlightQuery (departure_date >= today)
@model_validator(mode="after")
def validate_departure_not_in_past(self) -> Self:
    """Validate departure date is not in the past."""
    if self.departure_date < datetime.now().date():
        raise ValueError("Departure date cannot be in the past")
    return self
```

**Note on ordering:** Pydantic v2 runs multiple `@model_validator(mode="after")` decorators on the same model. When `validate_dates` and the new validators are on `FlightQuery`, they all run. The existing `validate_dates` handles `return_date > departure_date`; the new validators handle separate rules. No ordering conflict.

### Pattern 3: Pytest Fixture Factory with Keyword Overrides

**What:** A plain function (not necessarily a pytest fixture) that returns a fully-valid domain model. Callers override only the fields relevant to their assertion.
**When to use:** When multiple tests need to construct the same domain object with slight variations.

```python
# New file: backend/tests/fixtures/flights.py [ASSUMED — design pattern]
from datetime import UTC, datetime
from decimal import Decimal
from app.models import Flight, FlightQuery

def create_mock_flight(
    *,
    id: str = "FL-TEST-001",
    origin: str = "LAX",
    destination: str = "JFK",
    departure: datetime = datetime(2099, 6, 1, 10, 0, tzinfo=UTC),
    arrival: datetime = datetime(2099, 6, 1, 18, 30, tzinfo=UTC),
    price: Decimal = Decimal("450.00"),
    currency: str = "USD",
    carrier: str = "Test Airlines",
    flight_number: str = "TA100",
    duration_minutes: int = 330,
    stops: int = 0,
    booking_class: str = "economy",
) -> Flight:
    return Flight(
        id=id, origin=origin, destination=destination,
        departure=departure, arrival=arrival, price=price,
        currency=currency, carrier=carrier, flight_number=flight_number,
        duration_minutes=duration_minutes, stops=stops,
        booking_class=booking_class,
    )
```

**Key design rules from CONTEXT.md:**
- All parameters are keyword-only (`*,` in the signature) to prevent positional arg order mistakes
- Defaults produce a valid model with no required args — caller specifies only deviation fields
- Future-dated defaults (2099) keep tests valid without `freezegun`
- One function per model type: `create_mock_flight()`, `create_mock_flight_query()`

### Pattern 4: SSE Event Parser

**What:** Parses a raw SSE response body into a list of `StreamEvent` objects. Skips blank lines and keep-alive comments. Parses `data: {...}` lines only.
**When to use:** Integration tests that assert on the event stream from the chat endpoint.

```python
# New file: backend/tests/utils/sse.py [ASSUMED — design pattern]
import json
from app.models import StreamEvent

def parse_sse_events(text: str | list[str]) -> list[StreamEvent]:
    """Parse raw SSE response body into typed StreamEvent list.
    
    Skips blank lines and keep-alive comments (: keepalive).
    Only parses 'data: {...}' lines.
    """
    if isinstance(text, list):
        lines = text
    else:
        lines = text.strip().split("\n")
    
    events: list[StreamEvent] = []
    for line in lines:
        if not line.startswith("data: "):
            continue
        payload = line[len("data: "):]
        events.append(StreamEvent.model_validate(json.loads(payload)))
    return events
```

**Existing inline usage (refactor target):** `test_session.py` lines 60-63 contains the equivalent inline logic without type validation. [VERIFIED: codebase read]

### Anti-Patterns to Avoid

- **Duplicate `@model_validator` logic:** Do not add a second `validate_dates`-style check that overlaps with the existing one. The existing validator handles `return_date > departure_date`; new validators handle orthogonal rules.
- **Mutable default arguments in factory:** Use keyword-only args; never use a mutable default like `departure=datetime.now()` — it evaluates once at import time.
- **`freezegun` for departure-date tests:** D-01 locked this out. Use `PAST_DATE = date(2020, 1, 1)` and `FUTURE_DATE = date(2099, 1, 1)` constants in the test module.
- **Importing orphan components:** After deletion, running `tsc --noEmit` is the verification gate. The frontend's `noUnusedLocals` does not catch dead files — only dead variables. File existence without import is silent; deletion is the only fix.

## Common Pitfalls

### Pitfall 1: `@model_validator` Execution Order on FlightQuery

**What goes wrong:** Adding a new `@model_validator(mode="after")` that depends on normalized field values (e.g., uppercased IATA codes) may run before or after field validators, leading to tests that pass with lowercase input but fail for the wrong reason.
**Why it happens:** Pydantic v2 runs `@field_validator` before `@model_validator(mode="after")`, so IATA normalization is guaranteed to have run when the model validator executes.
**How to avoid:** Cross-field validators (`origin != destination`) can safely compare `self.origin == self.destination` after field validation, since both fields will already be uppercased. [VERIFIED: Pydantic v2 docs behavior — field validators run first]
**Warning signs:** Tests that pass lowercase `"lax"` to `origin` and expect a "same airport" error on `"LAX" == "LAX"` would fail if order were wrong.

### Pitfall 2: New `validate_dates` Validators Conflict with Existing One

**What goes wrong:** Adding a `departure_date >= today` validator that also checks `return_date`, accidentally duplicating or conflicting with the existing `validate_dates` check.
**Why it happens:** The existing `validate_dates` raises `ValueError("Return date must be after departure date")` if `return_date <= departure_date`. A new validator must not re-raise a different error for the same condition, or tests will see duplicate/confusing error messages.
**How to avoid:** Keep each `@model_validator` focused on a single orthogonal rule. The departure-date validator only checks `departure_date >= today`. The origin-destination validator only checks `origin != destination`. Let `validate_dates` continue to own `return_date > departure_date`.
**Warning signs:** Tests checking `ValidationError.errors()` find two errors for the same field pair.

### Pitfall 3: `Flight` Arrival-Before-Departure Not Caught by Existing Tests

**What goes wrong:** The existing `test_mock_client.py` line 91 asserts `assert flight.arrival > flight.departure` — this checks the mock client's output, not the model validation. Adding the `@model_validator` to `Flight` does not break this test, but the mock client generates flights where arrival > departure, so this assertion will continue to pass. The new validator tests specifically test with `arrival <= departure` input and must raise `ValidationError`.
**Why it happens:** Confusion between "the mock always generates valid data" (passing test) and "the model correctly rejects invalid data" (new test).
**How to avoid:** New validator tests explicitly construct a `Flight` with `arrival=departure` and assert `ValidationError` is raised. These are distinct from the mock client tests.
**Warning signs:** Thinking the mock client test coverage is sufficient for the new validator.

### Pitfall 4: `parse_sse_events()` Receives `TestClient` Response vs. Raw Text

**What goes wrong:** `TestClient` responses return `response.text` as a single string with `\n\n` as SSE event separators. Splitting on `\n` is correct; splitting on `\n\n` yields entire events (including `data:` prefix). Passing `response.text` directly to `parse_sse_events()` requires the function to handle the single-string case.
**Why it happens:** D-05 says the function accepts `str | list[str]`. When receiving `str`, the function must `strip().split("\n")` before processing — matching the existing inline pattern in `test_session.py`.
**How to avoid:** The reference implementation above handles both `str` and `list[str]` input. Verify by running the existing `test_session.py::TestChatInvalidSession::test_invalid_session_streams_empty_error_event` with the refactored helper.

### Pitfall 5: `FlightSegment` Validator and Factory — Scope Gap

**What goes wrong:** CONTEXT.md D-03 and D-07 specify that the `arrival > departure` validator and factory apply to `FlightSegment`. However, `FlightSegment` does not exist in the current `04.8` branch (it's a Phase 4.6 model in the `04.7` worktree). Implementing a validator for a non-existent model will cause an import error.
**Why it happens:** Phase 4.8 is being worked on in a branch that predates Phase 4.6's merge. The git log confirms the 4.8 branch was created before 4.4-4.7 were merged.
**How to avoid:** Scope the implementation to models that exist in the current branch (`Flight` and `FlightQuery`). When Phase 4.7 is merged in, add the `FlightSegment` validator and factory function as part of that merge integration. See Open Questions #1.
**Warning signs:** `from app.models import FlightSegment` raises `ImportError`.

### Pitfall 6: Frontend TypeScript Check Must Use Local `tsc`

**What goes wrong:** Running `tsc --noEmit` fails with "command not found" because `tsc` is not on PATH in this environment; it must be invoked via `node_modules/.bin/tsc` from the main tree (the worktree shares the parent `node_modules`).
**Why it happens:** Frontend `node_modules` are not installed in the worktree-local path — they exist at `/Users/axel/code/trip_planner/frontend/node_modules/`.
**How to avoid:** Use `just check` which runs the correct backend check commands. For frontend-only tsc: `cd /Users/axel/code/trip_planner/frontend && node_modules/.bin/tsc --noEmit`. The worktree frontend directory shares sources but not `node_modules`.
**Warning signs:** Running `npm run build` in the worktree fails with `sh: tsc: command not found`.

FastAPI handles `ValidationError` automatically. No custom exception handler is needed. [VERIFIED: existing test_chat.py line 85 demonstrates this pattern]

The 422 response body follows the standard Pydantic v2 format:
```json
{
    "detail": [
        {
            "type": "value_error",
            "loc": ["body"],
            "msg": "Value error, Arrival must be after departure",
            "input": {...},
            "ctx": {"error": "Arrival must be after departure"}
        }
    ]
}
```

Note: `model_validator` errors appear with `loc: ["body"]` (whole-body location), not a specific field path — this is standard Pydantic v2 behavior. [ASSUMED — standard Pydantic v2 behavior for model-level validators; field-level validators use field path]
