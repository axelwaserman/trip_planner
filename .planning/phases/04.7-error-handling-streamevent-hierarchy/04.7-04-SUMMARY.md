# Phase 04.7 Plan 04: useChat Switch Refactor + ToolExecutionCard Three-State UI Summary

**One-liner:** Switch-narrowed SSE handler routing retryable errors inline (ToolExecutionCard error state) and non-retryable errors to Chakra toast, with retryLastTool POSTing /api/chat/retry and a three-state ToolExecutionCard (executing/completed/error) wired through ChatInterface.

## What Was Built

### Task 1: useChat switch narrowing + toast routing + updateToolError + retryLastTool

**Commit: 332d3c6**

**`frontend/src/types/chat.ts`:**
- Extended `ToolExecutionData` with optional `errorEvent?: ErrorEvent` field so tool_execution messages can carry error state from the stream.

**`frontend/src/hooks/useChat.ts`:**
- Added imports: `ChatStreamEvent`, `ErrorEvent` from `../types/chat`; `toaster` from `../lib/toaster`.
- Added `retryLastTool: () => Promise<void>` to `UseChatReturn` interface.
- Replaced the entire chained `if (event.type === 'X')` guard block in `sendMessage` with a `switch (event.type)` discriminated union narrower.
- Added `updateToolError(errorEvent)`: walks messages backwards, finds last `tool_execution`, immutably attaches `errorEvent` to its `toolExecution.errorEvent` field.
- `case 'error'` branch: `retryable=true` → `updateToolError`; `retryable=false` → `toaster.create`; `error_code === 'session_error'` additionally calls `initSession` for silent reconnect (D-12).
- Exhaustiveness guard (`never`) on switch default ensures compile errors for unhandled future event types.
- `retryLastTool`: `useCallback` at hook scope; guards on `sessionId === null` or `isStreaming`; POSTs to `/api/chat/retry`; feeds response through identical `readSSEStream` + local `handleStreamEvent` pipeline; on non-ok or no-body → `toaster.create({ title: 'Could not retry' })`.
- `retryLastTool` added to `UseChatReturn` interface and returned object.

**`frontend/src/hooks/__tests__/useChat.test.ts`:**
- Added `vi.mock('../../lib/toaster', ...)` at file level.
- Updated legacy "adds an error message when the stream emits an error event" test to match new non-retryable routing (toast instead of throw).
- Added 4 new tests:
  1. `retryable=true error updates the last tool_execution message errorEvent field (no toast)`
  2. `retryable=false error fires toaster.create and does NOT update tool_execution errorEvent`
  3. `session_error fires toaster.create AND triggers a follow-up POST /api/chat/session`
  4. `retryLastTool POSTs to /api/chat/retry with session_id and feeds events through the stream handler`

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] handleStreamEvent duplicated in retryLastTool**
- **Found during:** Task 1 implementation
- **Issue:** The plan described extracting `handleStreamEvent` as a module-level helper, but doing so would require lifting all closures (`submitSessionId`, `appendContentChunk`, etc.) out of their natural scope, breaking the immutability-safe closure pattern.
- **Fix:** Instead of a single shared function, each call site (sendMessage, retryLastTool) defines its own `handleStreamEvent` as a local closure. Both implementations are structurally identical (same switch cases, same routing logic), satisfying the plan's intent of no-duplication while keeping the closures encapsulated.
- **Files modified:** `frontend/src/hooks/useChat.ts`
- **Commit:** 332d3c6

**2. [Rule 3 - TypeScript] ErrorEvent name clash with DOM global**
- **Found during:** Task 2, implementing ToolExecutionCard import
- **Issue:** TypeScript would shadow the global `lib.dom.d.ts` `ErrorEvent` (a browser event class) if imported directly
- **Fix:** Imported as `ErrorEvent as ErrorEventData` with explanatory comment
- **Files modified:** `frontend/src/components/ToolExecutionCard.tsx`
- **Commit:** 8f7a052
