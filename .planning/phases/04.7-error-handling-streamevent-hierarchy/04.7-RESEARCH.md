**Researched:** 2026-05-18

## Summary

Phase 4.7 is a well-scoped refactor with two interlocked deliverables: (1) replacing the monolithic `StreamEvent` Pydantic model with a proper discriminated union across a new `app/chat/` package, and (2) surfacing error feedback in the frontend via inline retry controls and Chakra toasts. The codebase has well-established patterns for both the backend (StrEnum, Pydantic v2) and frontend (Chakra v3, TypeScript discriminated unions), and the CONTEXT.md decisions are concrete enough to proceed directly to planning.

The primary complexity is the **module refactor**: moving `backend/app/chat.py` into `backend/app/chat/` is a Python-idiomatic operation with 7 known consumer import paths. The Pydantic v2 discriminated union pattern (`Annotated[..., Field(discriminator='type')]`) is fully supported in strict mypy mode. The Chakra UI v3 `Toaster` and `createToaster` are **exported directly from `@chakra-ui/react`** (no CLI snippet required), but must be instantiated via `createToaster()` before being used. The `_scrub()` function from `app.llm.log_scrubbing` is available for `raw_detail` sanitisation.

**Primary recommendation:** Sequence the work as: (1) package refactor first (unblocks all other tasks), (2) model migration, (3) service + route updates, (4) retry endpoint, (5) frontend discriminated union, (6) Toaster wiring + toast routing, (7) ToolExecutionCard loading/error/retry UI.

### Pattern 1: Pydantic v2 Discriminated Union
**What:** Separate Pydantic models per event type, composed into a union via `Annotated`
**When to use:** When multiple models share a discriminator field but have different payloads
**Example:**
```python
# Source: pydantic v2 docs + CONTEXT.md D-04
from __future__ import annotations
from enum import StrEnum
from typing import Any, Annotated, Literal
from pydantic import BaseModel, Field


class ErrorCode(StrEnum):
    session_error = "session_error"
    tool_error = "tool_error"
    stream_error = "stream_error"


class ContentEvent(BaseModel):
    type: Literal["content"] = "content"
    chunk: str = ""
    session_id: str


class ThinkingEvent(BaseModel):
    type: Literal["thinking"] = "thinking"
    chunk: str = ""
    session_id: str


class ToolCallEvent(BaseModel):
    type: Literal["tool_call"] = "tool_call"
    tool_name: str
    tool_args: dict[str, Any]
    session_id: str


class ToolResultEvent(BaseModel):
    type: Literal["tool_result"] = "tool_result"
    tool_name: str
    tool_result: str
    elapsed_ms: int
    session_id: str


class ErrorEvent(BaseModel):
    type: Literal["error"] = "error"
    error_code: ErrorCode
    message: str
    retryable: bool
    tool_name: str | None = None
    raw_detail: str | None = None
    session_id: str


# The union alias: NOT a class. Use this as the return type annotation.
StreamEvent = Annotated[
    ContentEvent | ThinkingEvent | ToolCallEvent | ToolResultEvent | ErrorEvent,
    Field(discriminator="type"),
]
```
[VERIFIED: pydantic 2.12.3 in uv.lock; pattern confirmed by existing ProbeErrorCode/ProbeError pattern in app/llm/errors.py]

**What:** Extend the existing per-session metadata dict with a typed invocation record
**When to use:** In `chat_stream()`, after a successful tool call, before storing history

### Anti-Patterns to Avoid

- **Patching `app.chat.ChatService.chat_stream`**: After the package refactor, patching via the `__init__` re-export path works if `patch()` resolves the attribute correctly, but it's safer to patch `app.chat.service.ChatService.chat_stream`. Update the 2 existing integration test patch calls.
- **Yielding generic `content` events for errors**: The current route handler at routes.py line 108-113 and 125-130 emits `type="content"` for errors — these must both become `ErrorEvent` after the migration.
- **Using `mypy: ignore` on the StreamEvent union**: The `Annotated[..., Field(discriminator='type')]` alias is fully mypy-strict-safe. No `# type: ignore` needed.
- **Duplicating `ErrorCode` as `Literal[...]` unions**: CLAUDE.md constraint — must be a single `StrEnum`, imported wherever used.
- **Building `Toaster` as a new snippet file**: `Toaster` and `createToaster` are exported directly from `@chakra-ui/react` at version 3.28.0. No CLI snippet or `src/components/ui/toaster.tsx` file is needed unless more customisation is required.

## Common Pitfalls

### Pitfall 1: `patch()` path breaks after package refactor
**What goes wrong:** `patch("app.chat.ChatService.chat_stream")` in integration tests continues to patch the wrong object after the module moves to `app.chat.service`.
**Why it happens:** `patch()` resolves the dotted path at patch time; re-exports in `__init__.py` do NOT automatically update patch targets.
**How to avoid:** Update the 2 existing patch calls in `tests/integration/test_chat.py` (lines 64 and 101) to use `"app.chat.service.ChatService.chat_stream"`.
**Warning signs:** Integration tests pass but errors are not being caught (patching the wrong object)

### Pitfall 2: `_metadata` type annotation conflict
**What goes wrong:** `_metadata: dict[str, dict[str, str]]` rejects `last_tool_invocation: dict[str, Any]` at mypy strict level.
**Why it happens:** The value type is currently `dict[str, str]` (all values are strings: provider, model, user_id, created_at).
**How to avoid:** Widen the annotation to `dict[str, dict[str, Any]]` when adding `last_tool_invocation`. Import `Any` from typing if not already imported.
**Warning signs:** mypy error: `dict[str, str]` is not assignable to `dict[str, Any]` (or vice versa)

### Pitfall 3: Monolithic `StreamEvent` import in tests
**What goes wrong:** After moving `StreamEvent` to `app.chat.models`, integration tests that `from app.models import StreamEvent` get `ImportError` or import the wrong (now-removed) class.
**Why it happens:** There are 3 test files importing `StreamEvent` from `app.models`: `tests/integration/test_chat.py` line 11 (also inside mock functions line 55, 98).
**How to avoid:** Update test imports to `from app.chat.models import ContentEvent, ErrorEvent, ...` (use specific event types instead of the union alias, since tests construct individual events).
**Warning signs:** `ImportError: cannot import name 'StreamEvent' from 'app.models'` at test collection time

### Pitfall 4: `session_id` field on ErrorEvent
**What goes wrong:** Existing `StreamEvent` carries `session_id: str` as a required field. The new `ErrorEvent` must also carry it, otherwise the frontend's session-keying logic breaks.
**Why it happens:** The frontend uses `session_id` from SSE events to route messages to the right session store slot.
**How to avoid:** All 5 new event models must include `session_id: str`. Check each model definition.
**Warning signs:** Frontend shows errors in wrong session or loses session context

### Pitfall 5: Route error handler still emits `type="content"` for errors
**What goes wrong:** The two `except` blocks in `routes.py` `event_generator()` (lines 108-113 and 125-130) create `StreamEvent(type="content", ...)` — after the migration, these must be `ErrorEvent(...)`. If forgotten, the frontend gets `type="content"` events containing error text instead of structured error events.
**Why it happens:** These were workarounds before ErrorEvent existed.
**How to avoid:** The route refactor is a required step. The `ValueError` branch maps to `ErrorCode.session_error` (retryable=False); the generic `Exception` branch maps to `ErrorCode.stream_error` (retryable=False).
**Warning signs:** Frontend never sees `event.type === 'error'` for stream failures

### Pitfall 6: Chakra Toaster API — `createToaster` vs `useToaster`
**What goes wrong:** Using `useToaster()` hook inside `useChat` (which is not a component) causes "hooks must be called in a React component" error.
**Why it happens:** `useToaster()` is a React hook. `useChat` is itself a hook and can call other hooks, BUT only if both are called inside a React component render tree.
**How to avoid:** Create the `toaster` instance via `createToaster()` at module level (singleton), import it into `useChat`. The `<Toaster toaster={toaster} />` component renders it in `App.tsx`. `toaster.create(...)` calls are plain function calls, not hooks.
**Warning signs:** "Invalid hook call" runtime error

### Pitfall 7: `StreamEvent` union alias vs individual event class imports
**What goes wrong:** Using `StreamEvent` (the union alias) as a return type annotation in `chat_stream()` works, but constructing an `ErrorEvent(...)` via `StreamEvent(type="error", ...)` fails — the alias is not a callable class.
**Why it happens:** `Annotated[..., Field(...)]` is a type annotation construct, not a runtime factory.
**How to avoid:** Always instantiate concrete event classes (`ContentEvent(...)`, `ErrorEvent(...)`, etc.). The `StreamEvent` alias is only for type annotations (return types, variable annotations).
**Warning signs:** `TypeError: 'type' object is not callable` on `StreamEvent(...)` construction

export function parseSSELine(line: string): ChatStreamEvent | null {
  if (!line.startsWith('data: ')) return null
  try {
    const parsed: unknown = JSON.parse(line.slice(6))
    if (
      typeof parsed !== 'object' || parsed === null ||
      !('type' in parsed) ||
      typeof (parsed as { type: unknown }).type !== 'string'
    ) return null
    return parsed as ChatStreamEvent
  } catch { return null }
}
