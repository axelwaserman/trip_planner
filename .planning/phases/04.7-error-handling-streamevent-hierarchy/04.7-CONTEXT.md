<domain>
## Phase Boundary

Two interlocked deliverables:

1. **StreamEvent discriminated union** — Replace the monolithic `StreamEvent` Pydantic model with separate models (`ContentEvent | ThinkingEvent | ToolCallEvent | ToolResultEvent | ErrorEvent`) in a new `backend/app/chat/` package. Introduce `app/chat/models.py` as the chat-domain model home (introducing the `app/chat/` package). Update SSE serialization in the backend and `parseSSE` / `useChat` on the frontend to use a TypeScript discriminated union. The frontend `types/chat.ts` becomes a proper TS discriminated union narrowed in switch statements.

2. **UX-grade error feedback** — Surface the new `ErrorEvent` type in the UI: inline errors with a retry button inside `ToolExecutionCard` for retryable tool errors; toast notifications (Chakra `Toaster` wired into `App.tsx`) for non-retryable errors; loading state in `ToolExecutionCard` while a tool call is in flight. A new `POST /api/chat/retry` endpoint replays the last tool invocation from stored session metadata.

**In scope:**
- `backend/app/chat/` package with `models.py` housing the discriminated union event types
- `ErrorCode` StrEnum (3 values: `session_error`, `tool_error`, `stream_error`)
- `ErrorEvent` with `error_code`, `message`, `retryable`, `tool_name`, `raw_detail` fields
- `POST /api/chat/retry` endpoint — replays last tool invocation, re-streams full LLM turn
- `ChatService._metadata[session_id]` grows a `last_tool_invocation` field
- `ToolExecutionCard` loading state + inline error + retry button
- Chakra `Toaster` in `App.tsx`; `useToaster()` called from `useChat`
- Session-error recovery: auto-create new session silently + show toast
- Frontend `types/chat.ts` refactored into proper TypeScript discriminated union
- `parseSSE` and `useChat` updated to switch-narrow over event types

**Out of scope (deferred):**
- Full in-memory event log per session → Phase 5 (Postgres-backed event persistence)
- Tool-set switching (choosing which tools the agent has available per retry) → Phase 5+
- `raw_detail` rendering visible to end users in production UI (backend emits it; frontend may choose to expose in dev/debug mode only)

<decisions>
## Implementation Decisions

### ErrorEvent Payload

- **D-01: Error taxonomy is minimal — 3 codes as a `StrEnum`: `session_error | tool_error | stream_error`.**
  Defined once in `backend/app/chat/models.py` (following CLAUDE.md StrEnum constraint: cross-module string codes must be a StrEnum, not duplicated `Literal` unions). Maps 1:1 to the three error origins in REQUIREMENTS.md.

- **D-02: `ErrorEvent` carries: `type: Literal["error"]`, `error_code: ErrorCode`, `message: str`, `retryable: bool`, `tool_name: str | None`, `raw_detail: str | None`.**
  `retryable` drives whether the frontend shows a retry control. `tool_name` identifies which tool errored so `ToolExecutionCard` can display the error inline. `raw_detail` = `str(exception)` run through the Phase 4.5 log scrubber (strips `api_key` / `sk-...` patterns).

- **D-03: `raw_detail` is always populated by the backend (never `None` when an exception is the cause); the frontend decides whether to render it.**
  Backend always emits it via `str(exception)` through the existing scrubber. Frontend may hide it in production builds or expose in a collapsible dev section — the rendering decision is frontend-local.

### Discriminated Union Shape

- **D-04: Backend uses separate Pydantic models per event type + `Annotated` union with `discriminator='type'`.**
  `ContentEvent`, `ThinkingEvent`, `ToolCallEvent`, `ToolResultEvent`, `ErrorEvent` — each model carries only its own fields. Each model's `type` field is a `Literal["content"]` etc. The union type alias:
  ```python
  StreamEvent = Annotated[
      ContentEvent | ThinkingEvent | ToolCallEvent | ToolResultEvent | ErrorEvent,
      Field(discriminator="type")
  ]
  ```
  This is Pydantic v2 native and mypy-strict-safe.

- **D-05: Event models live in `backend/app/chat/models.py`.**
  Introduces an `app/chat/` package (alongside existing `app/llm/` and `app/tools/`). The new `chat/models.py` becomes the chat-domain model home; it co-locates event types with the chat service. `app/models.py` retains domain models (`Flight`, `FlightQuery`, etc.) but the `StreamEvent` monolith moves out.
  > **Planner note:** `backend/app/chat.py` must be refactored into a package (`app/chat/__init__.py` or `app/chat/service.py`) as part of this reorganisation. `ChatService` import paths will change — update all consumers.

- **D-06: Frontend `types/chat.ts` becomes a proper TypeScript discriminated union.**
  Separate interfaces per event type; the union is narrowed in `parseSSE` and `useChat` via `switch (event.type)`. This removes the flat `StreamEvent` interface with many optional fields and provides compile-time narrowing guarantees.

### Retry Mechanic

- **D-07: New `POST /api/chat/retry` endpoint — replays the last tool invocation stored on session metadata.**
  `ChatService._metadata[session_id]` grows a `last_tool_invocation: dict[str, Any] | None` field (tool name + args). `POST /api/chat/retry` reads this, re-invokes the tool, and re-streams the full LLM turn (ToolCallEvent → ToolResultEvent → reasoning → final response) — same code path as `chat_stream`, starting from the stored invocation.

- **D-08: Full event log + tool-set switching deferred to Phase 5.**
  Phase 4.7 tracks only `last_tool_invocation`. Full in-memory event log per session and the ability to retry any past event or change available tools are Phase 5 (Postgres-backed) concerns.

- **D-09: Retry re-streams the full LLM turn, not just the tool result.**
  User sees the agent recover naturally: tool call → tool result → LLM reasoning → final response. Consistent UX with a normal chat turn.

### Toast Routing

- **D-10: Routing rule: `retryable=True` → inline in `ToolExecutionCard` with retry button; `retryable=False` → Chakra toast.**
  Simple, driven by the `ErrorEvent.retryable` field. No frontend taxonomy logic needed. Non-retryable errors (session gone, stream interrupted) surface as toasts; retryable tool errors surface inline.

- **D-11: Chakra `Toaster` wired into `App.tsx`; `useToaster()` called from `useChat`.**
  Consistent with Chakra v3 pattern: `<Toaster />` inside `ChakraProvider` at root. Toast calls originate from `useChat` where `ErrorEvent` objects are handled.

- **D-12: On `session_error` (non-retryable): auto-create a new session silently + show toast.**
  Consistent with existing session-creation-on-load behaviour. User sees the toast ("Session expired — starting a new conversation") but chat remains usable. No redirect, no manual reconnect required.

</decisions>

<deferred>
## Deferred Ideas

- **Full in-memory event log per session** — user wants every session event persisted so any can be retried with context. Deferred to Phase 5 (Postgres-backed). Phase 4.7 tracks only `last_tool_invocation`.
- **Tool-set switching** — ability for the user to retry with a different set of tools available to the agent. Deferred to Phase 5+; requires both event log persistence and a tool-registry API.
