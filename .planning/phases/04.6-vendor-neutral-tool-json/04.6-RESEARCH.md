## Summary

Phase 4.6 redesigns the `search_flights()` tool return value from a formatted text string to a structured Pydantic model that maps cleanly onto real vendor APIs (primarily Amadeus). The two main work streams are:

**Backend:** Replace the `str` return type with a new `FlightSearchResult` Pydantic model hierarchy (`FlightSearchResult → FlightResult → FlightSegment → FlightEndpoint + CarrierInfo + PriceInfo`). The mock client's `search()` already returns `list[Flight]`; the tool adapter translates those into the new shape. The new models live alongside the existing `Flight`/`FlightQuery` models in `app/models.py` (or a new `app/models/flight_search.py`). The tool's docstring still guides the LLM; the structured result object is serialized to JSON via `model_dump()` before being embedded in the SSE `tool_result` event payload.

**Frontend:** `ToolExecutionCard` currently receives `tool_result` as a plain string and renders it through `ReactMarkdown`. The new contract delivers a parsed JSON object (or a JSON-serializable string the component parses). The component gains a structured renderer: a `<Table>` for the `results[]` array, `<List>` for arrays, labelled sections for nested objects. The LLM's narrative response alongside the card is unchanged.

**Acceptance fixtures** validate that Amadeus and Skyscanner sample payloads normalize into the canonical shape without lossy field collapses. Google Flights has no public REST API; this fixture is documented as omitted.

**Primary recommendation:** Define the new Pydantic models first, derive the normalization functions from the fixtures, write unit tests against the fixtures, then update the tool and frontend.

### Pattern 1: New Model Hierarchy (Pydantic v2)

**What:** Replace the `str` return from `search_flights()` with a structured Pydantic model.
**When to use:** Tool result conveys rich structure the UI can render.

```python
# Source: Amadeus OpenAPI spec [VERIFIED] + project Pydantic v2 conventions

from decimal import Decimal
from datetime import datetime
from pydantic import BaseModel, Field


class FlightEndpoint(BaseModel):
    """Departure or arrival endpoint — maps to Amadeus FlightEndPoint."""
    iata_code: str = Field(..., description="IATA airport code")
    city: str = Field(..., description="City name")
    terminal: str | None = Field(default=None, description="Terminal name/number (optional)")
    at: datetime = Field(..., description="Local ISO-8601 datetime with timezone")


class CarrierInfo(BaseModel):
    """Carrier — maps to Amadeus carrierCode + carrier dictionaries."""
    iata_code: str = Field(..., description="IATA 2-letter airline code, e.g. 'DL'")
    name: str = Field(..., description="Display name, e.g. 'Delta Air Lines'")


class PriceInfo(BaseModel):
    """Price — maps to Amadeus Price.total + currency."""
    amount: Decimal = Field(..., description="Total price")
    currency: str = Field(default="USD", description="ISO 4217 currency code")


class FlightSegment(BaseModel):
    """Single flight leg — maps to Amadeus Segment."""
    id: str = Field(..., description="Segment identifier")
    departure: FlightEndpoint
    arrival: FlightEndpoint
    carrier: CarrierInfo
    flight_number: str = Field(..., description="Flight number as assigned by carrier")
    duration: str = Field(..., description="ISO 8601 duration string, e.g. 'PT5H30M'")
    number_of_stops: int = Field(default=0, ge=0)


class FlightResult(BaseModel):
    """A single bookable flight offer — normalised across vendors."""
    id: str
    segments: list[FlightSegment] = Field(..., min_length=1)
    total_duration: str = Field(..., description="Total journey duration (ISO 8601)")
    price: PriceInfo
    booking_class: str = Field(default="ECONOMY")


class FlightSearchQuery(BaseModel):
    """Echo of the search request parameters."""
    origin: str
    destination: str
    departure_date: str
    passengers: int = 1


class FlightSearchResult(BaseModel):
    """Canonical envelope returned by search_flights()."""
    status: str = Field(default="ok")
    query: FlightSearchQuery
    results: list[FlightResult]
    count: int
```

**Key design notes:**
- `FlightEndpoint.at` is a `datetime` with timezone — Pydantic serialises to ISO-8601 with offset when `model_dump(mode="json")` is used.
- `PriceInfo.amount` is `Decimal` (matching existing `Flight.price` type) — avoids float precision loss.
- `FlightSegment` deliberately mirrors Amadeus `Segment` (departure/arrival/carrierCode/number/duration) to minimise Phase 7 rework.
- `segments[]` supports multi-leg itineraries; a direct flight has exactly one segment.
- `booking_class` is a string (not `Literal`) to remain additively extendable without a breaking change.

### Pattern 2: Adapter Function in `flight_search.py`

**What:** A pure function translates `list[Flight]` + `FlightQuery` into `FlightSearchResult`.
**When to use:** The mock client returns `list[Flight]`; the real client (Phase 7) will do the same via the `FlightAPIClient.search()` ABC contract.

```python
# Source: project patterns — Functional Service Pattern from ARCHITECTURE.md

from datetime import timedelta
from app.models import Flight, FlightQuery, FlightSearchResult  # (new models)

# Carrier IATA code is not in the current Flight model.
# The existing MockFlightAPIClient stores CARRIERS dict: {"AA": "American Airlines", ...}
# The Flight model only has `carrier` (full name) and `flight_number` (e.g. "AA123").
# Adapter derives iata_code by slicing the flight_number prefix.

def _extract_carrier_iata(flight: Flight) -> str:
    """Best-effort IATA extraction from flight_number prefix (e.g. 'AA123' -> 'AA')."""
    import re
    m = re.match(r'^([A-Z]{2})', flight.flight_number)
    return m.group(1) if m else "ZZ"


def _to_iso_duration(minutes: int) -> str:
    """Convert integer minutes to ISO 8601 duration string."""
    h, m = divmod(minutes, 60)
    return f"PT{h}H{m}M" if m else f"PT{h}H"


def _to_flight_search_result(flights: list[Flight], query: FlightQuery) -> FlightSearchResult:
    results = []
    for flight in flights:
        iata = _extract_carrier_iata(flight)
        results.append(FlightResult(
            id=flight.id,
            segments=[
                FlightSegment(
                    id=f"{flight.id}-s1",
                    departure=FlightEndpoint(
                        iata_code=flight.origin,
                        city=flight.origin,   # MockClient has no city name — use IATA as placeholder
                        at=flight.departure,
                    ),
                    arrival=FlightEndpoint(
                        iata_code=flight.destination,
                        city=flight.destination,
                        at=flight.arrival,
                    ),
                    carrier=CarrierInfo(iata_code=iata, name=flight.carrier),
                    flight_number=flight.flight_number,
                    duration=_to_iso_duration(flight.duration_minutes),
                    number_of_stops=flight.stops,
                )
            ],
            total_duration=_to_iso_duration(flight.duration_minutes),
            price=PriceInfo(amount=flight.price, currency=flight.currency),
            booking_class=flight.booking_class.upper(),
        ))
    return FlightSearchResult(
        status="ok",
        query=FlightSearchQuery(
            origin=query.origin,
            destination=query.destination,
            departure_date=str(query.departure_date),
            passengers=query.passengers,
        ),
        results=results,
        count=len(results),
    )
```

**Caveat on `city` field:** `MockFlightAPIClient` does not store city names; it only knows IATA codes. The adapter uses the IATA code as a city placeholder. Phase 7's real Amadeus client returns city names in the `dictionaries.locations[iataCode].cityCode` field — the `FlightEndpoint.city` field must remain in the model to avoid a breaking change. The tests for the mock adapter should pass when `city == iata_code`.

### Pattern 4: `ToolExecutionCard` Structured Renderer

**What:** Detect structured flight result and render as table. Fall back gracefully to `ReactMarkdown` if JSON parse fails or shape is unrecognised.

```typescript
// Source: project pattern — Chakra UI Table v3 + TypeScript patterns from CLAUDE.md

interface FlightEndpointData {
  iata_code: string
  city: string
  terminal?: string
  at: string
}
interface CarrierInfoData {
  iata_code: string
  name: string
}
interface FlightSegmentData {
  id: string
  departure: FlightEndpointData
  arrival: FlightEndpointData
  carrier: CarrierInfoData
  flight_number: string
  duration: string
  number_of_stops: number
}
interface FlightResultData {
  id: string
  segments: FlightSegmentData[]
  total_duration: string
  price: { amount: string; currency: string }
  booking_class: string
}
interface FlightSearchResultData {
  status: string
  query: { origin: string; destination: string; departure_date: string; passengers: number }
  results: FlightResultData[]
  count: number
}

function isFlightSearchResult(value: unknown): value is FlightSearchResultData {
  if (typeof value !== 'object' || value === null) return false
  const v = value as Record<string, unknown>
  return (
    typeof v.status === 'string' &&
    Array.isArray(v.results) &&
    typeof v.count === 'number'
  )
}
```

### Anti-Patterns to Avoid

- **Returning `str` from `search_flights()`:** The current approach strings-format flight data for the LLM. After this phase the LLM gets the JSON string — the docstring must still guide the LLM to narrate it naturally in prose. The JSON is for the card renderer, not the LLM's "answer".
- **Mutating the `Flight` model:** The Phase 7 client targets the same `FlightAPIClient.search()` contract which returns `list[Flight]`. Do not add vendor-specific fields to `Flight`; add them to `FlightResult` instead.
- **Storing city names in `MockFlightAPIClient`:** The mock is a test fixture, not a reference implementation. City lookups belong in a reference-data helper that the real Phase 7 client provides. The mock simply uses IATA as a placeholder.
- **Parsing JSON in `chat.py`:** The `chat.py` SSE loop does `tool_result=str(tool_result)` and passes it as a string. The structured parsing happens in the frontend. Do not add JSON parsing logic to `chat.py` — that would break the clean tool ↔ LLM contract.
- **Hardcoding Chakra Table API:** Chakra UI v3 changed Table's prop API from v2. Use `Table.Root`, `Table.Header`, `Table.Body`, `Table.Row`, `Table.ColumnHeader`, `Table.Cell` — not the old `<Th>`, `<Td>` props. See below in Code Examples.

## Common Pitfalls

### Pitfall 1: Amadeus datetimes have no timezone offset
**What goes wrong:** Amadeus `departure.at` is `"2017-10-23T20:00:00"` — a local datetime string with **no UTC offset**. Pydantic's `datetime` field with `model_validate()` will parse this as a naive (timezone-unaware) datetime, violating the REQ-tool-json-output requirement for "ISO-8601 timestamps with timezone."
**Why it happens:** Amadeus docs say: "local date and time in ISO8601 YYYY-MM-ddThh:mm:ss format."
**How to avoid:** In the Phase 7 normalization adapter, append `+00:00` for unknown TZ or look up the IATA airport's timezone. For the Phase 4.6 **mock** fixture, the test data should supply timezone-aware strings (`"2026-06-15T08:00:00-07:00"` for LAX) so the test exercises TZ-aware parsing.
**Warning signs:** `TypeError: can't compare offset-naive and offset-aware datetimes` in tests.

### Pitfall 2: Decimal vs float in price fields
**What goes wrong:** Skyscanner `price.raw` is a float (`450.50`). Pydantic v2 will accept a float into a `Decimal` field, but `Decimal(450.50)` is `Decimal('450.4999999999999715782905695...)` — lossy.
**Why it happens:** Float-to-Decimal conversion does not round-trip through the decimal representation.
**How to avoid:** Convert via string: `Decimal(str(raw_price))`. Add a `@field_validator` on `PriceInfo.amount` that coerces `float` input via `str()`.
**Warning signs:** Test assertion `result.price.amount == Decimal("450.50")` fails with a bizarre decimal value.

### Pitfall 3: Amadeus carrier name requires dictionary lookup
**What goes wrong:** Amadeus segments contain only `carrierCode: "DL"`. The carrier display name `"Delta Air Lines"` lives in the top-level `response.data[].dictionaries.carriers` dict. Normalization code that ignores the dictionaries will populate `CarrierInfo.name` with the IATA code instead of the display name.
**Why it happens:** Amadeus separates reference data from offer data to avoid repetition.
**How to avoid:** The normalization function for Amadeus must accept `dictionaries: dict` as a parameter. The test fixture must include the `dictionaries` object.
**Warning signs:** `carrier.name == "DL"` instead of `"Delta Air Lines"` in test assertions.

### Pitfall 4: Chakra UI v3 Table API differs from v2
**What goes wrong:** Copy-pasting Chakra v2 `<Table>`, `<Th>`, `<Td>` usage. Chakra v3 uses a compound component API: `<Table.Root>`, `<Table.Header>`, `<Table.Body>`, `<Table.Row>`, `<Table.ColumnHeader>`, `<Table.Cell>`.
**Why it happens:** Major version break in Chakra UI component API between v2 and v3.
**How to avoid:** Import from `@chakra-ui/react` and use v3 Table anatomy. See Code Examples below.
**Warning signs:** TypeScript errors like "Property 'colorScheme' does not exist on 'Table'" or runtime `undefined is not a function`.

### Pitfall 5: `tool_result` as JSON string vs JSON object in SSE
**What goes wrong:** The SSE `StreamEvent.tool_result` field is currently typed as `str | None`. The backend passes `model_dump_json()` (a JSON string). The frontend's `useChat.ts` stores this string into `resultMetadata.full_result`. If `ToolExecutionCard` tries to render `full_result` directly through `ReactMarkdown`, it will show the raw JSON string.
**Why it happens:** The current flow was designed for formatted text, not JSON.
**How to avoid:** In `ToolExecutionCard`, attempt `JSON.parse(full_result)` first. If it parses and `isFlightSearchResult(parsed)` returns `true`, render the structured view. Otherwise, fall back to `<ReactMarkdown>`.
**Warning signs:** UI shows `{"status":"ok","query":{...},"results":[...]}` as plain text.

### Pitfall 6: Skyscanner `legs` vs `segments` mapping confusion
**What goes wrong:** Skyscanner uses `itinerary.legs[]` where each leg maps to a full O/D pair (what Amadeus calls a segment). Skyscanner *also* has `leg.segments[]` for technical stops. Mapping Skyscanner `legs[].segments[]` directly to our `FlightResult.segments[]` would create an extra nesting level.
**Why it happens:** Terminology mismatch between APIs.
**How to avoid:** Map Skyscanner `leg` → `FlightResult`, and Skyscanner `leg.segments[]` → `FlightResult.segments[]`. The test fixture must exercise this correctly.
