# Phase 4.6: Vendor-Neutral Tool JSON - Context

**Gathered:** 2026-05-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4.6 has two intertwined deliverables:

1. **Backend domain restructure** — migrate `backend/app/` from a flat layout to domain modules (`auth/`, `chat/`, `tools/`). `config.py` and `exceptions.py` stay at the `app/` root as app-wide singletons. No `shared/` module; introduce `core/` only if a genuine cross-domain need arises. This is a pure refactor — no behaviour change.

2. **Vendor-neutral tool JSON contract** — `search_flights()` is redesigned from a `str`-returning tool to one that returns a `FlightSearchResult` Pydantic model (defined in `backend/app/tools/schemas.py`). The shape maps cleanly onto Amadeus / Skyscanner / Google Flights field maps: `{status, query, results[], count}` where each result is an itinerary envelope with `segments[]` (full-leg breakout), IATA + city endpoints, ISO-8601 timestamped with timezone, `price: {amount, currency}`, and carrier as IATA + display name. `MockFlightAPIClient` generates real multi-segment data for 1-stop and 2-stop flights. `ToolExecutionCard` renders the structured result using native Chakra components (table, lists, labelled sections) — never a raw JSON blob.

**In scope:**
- `backend/app/` domain restructure: `auth/`, `chat/`, `tools/` modules; `config.py` + `exceptions.py` at app root
- `FlightSearchResult` Pydantic model in `backend/app/tools/schemas.py`
- `FlightSegment` model for itinerary legs (full-leg breakout, not stopover metadata)
- `search_flights()` returns `FlightSearchResult` (not `str`)
- `MockFlightAPIClient` generates segments[] for 1-stop and 2-stop flights
- `ChatService` serializes: `FlightSearchResult.to_llm_summary()` → `ToolMessage`; full JSON → SSE `tool_result.full_result`
- `ToolExecutionCard` native Chakra table + list renderer for structured flight data
- Frontend parses `full_result` JSON → typed `FlightSearchResult` → passes to card
- Normalization fixture tests against Amadeus / Skyscanner / Google Flights public samples (per ROADMAP acceptance fixture sources)

**Out of scope:**
- SSE `StreamEvent` discriminated union redesign → Phase 4.7
- Real Amadeus HTTP client → Phase 7
- `thinking` chunk scenario tests → Phase 4.5/4.7
- Frontend auth changes or provider selector changes
- New `core/` module unless a genuine cross-domain need surfaces during planning

</domain>

<decisions>
## Implementation Decisions

### Backend Structure Migration

- **D-01: Domain module layout.**
  Target: `backend/app/auth/` (routes.py, schemas.py, service.py, dependencies.py), `backend/app/chat/` (service.py, schemas.py), `backend/app/tools/` (flight_search.py, flight_client.py, retry.py, schemas.py). `config.py` and `exceptions.py` stay at `app/` root — they are app-wide, not domain-specific.

- **D-02: No `shared/` module.**
  Replace `shared/` with `core/` only if a genuine cross-domain need emerges during planning. Don't pre-create it. The FastAPI skill's domain-based layout is the reference — see `canonical_refs`.

- **D-03: Pure refactor — no behaviour change in migration wave.**
  The structural migration produces a green test suite with zero functional changes. Planner should treat this as a distinct wave before adding the tool JSON contract changes.

### Tool Return Contract

- **D-04: `search_flights()` returns `FlightSearchResult` Pydantic model.**
  Defined in `backend/app/tools/schemas.py`. Shape: `{status: str, query: FlightQuery, results: list[FlightItinerary], count: int}`. `search_flights` is a LangChain `@tool` — the return type annotation changes from `str` to `FlightSearchResult`. LangChain serializes it for the `ToolMessage`; `ChatService` intercepts and builds a text summary for the LLM.

- **D-05: `FlightItinerary` replaces `Flight` as the top-level result object.**
  Each itinerary is an envelope over `segments: list[FlightSegment]` plus derived summary fields (total duration, total price, number of stops). `FlightSegment` captures one leg: `{origin: {iata, city}, destination: {iata, city}, departure: datetime (ISO-8601 + tz), arrival: datetime (ISO-8601 + tz), carrier: {iata, name}, flight_number: str, duration_minutes: int}`. Price lives on `FlightItinerary`, not on the segment.

- **D-06: `MockFlightAPIClient` generates real multi-segment data.**
  1-stop flights produce 2 segments (origin→stop, stop→destination); 2-stop flights produce 3 segments. Stopover airport is invented deterministically from the RNG seed. Matches the Amadeus FlightOffer shape that Phase 7 will produce for real.

### Narration + Card Consistency

- **D-07: `ChatService` dual-path serialization.**
  After the tool call returns `FlightSearchResult`:
  1. Call `result.to_llm_summary()` → compact human-readable text → `ToolMessage.content` (what the LLM narrates from).
  2. `result.model_dump_json()` → `StreamEvent.full_result` (what the SSE `tool_result` event carries to the frontend card).
  The two paths are independent: LLM gets a summary, card gets full structured data.

- **D-08: `to_llm_summary()` is a method on `FlightSearchResult`.**
  Returns e.g. `"Found 5 flights LAX→JFK on 2026-06-01. Prices from $312 to $780 (economy). Fastest: 5h 15m direct on AA."` The LLM narrates naturally from this, without seeing raw JSON.

### Frontend Card Rendering

- **D-09: `ToolExecutionCard` receives typed `FlightSearchResult` props.**
  Frontend parses `event.full_result` as JSON → validates as `FlightSearchResult` shape → passes structured props. Card renders: a Chakra `Table` for `results[]` (itinerary rows with price, duration, stops), expandable `segments[]` per row as a list, and labelled sections for `query` context.

- **D-10: SSE wire contract unchanged for this phase.**
  `StreamEvent.full_result` carries JSON string. No new fields added to `StreamEvent` before Phase 4.7's discriminated union redesign. Frontend TypeScript type for `tool_result` events is extended to parse `full_result` as `FlightSearchResult | unknown` with a runtime guard.

### Claude's Discretion

- Whether `FlightItinerary` inherits from the current `Flight` model or replaces it entirely — planner should assess the migration blast radius and choose the cleanest path.
- Exact field names on `FlightSegment` for origin/destination city (e.g. `origin_city` vs `origin: {iata, city}` nested object) — whichever is more consistent with the Amadeus sample shape.
- Whether `to_llm_summary()` is a method or a standalone function in `tools/schemas.py` — method is cleaner (no import cycle risk).
- Test file layout for normalization tests — `backend/tests/unit/test_tool_json_normalization.py` per ROADMAP, or a subdirectory if fixtures are large.

</decisions>

- `auth_headers` + `TestClient(app)` fixtures in `conftest.py` — reuse for integration tests covering the new card path.

### Established Patterns
- **LangChain tool returns string** — the current convention. Phase 4.6 breaks this intentionally. The ROADMAP success criteria explicitly require returning `{status, query, results[], count}`. Any downstream agent that sees "tool must return str" guidance should override it for this tool.
- **Pydantic models in `models.py`** — the current flat layout. After migration, domain models live in `{domain}/schemas.py`. If planner sees `app.models` imports anywhere, those must be updated as part of the restructure wave.
- **SSE `StreamEvent.full_result`** is currently a `str` — stays `str` (carries JSON). Phase 4.7 replaces this field with typed variants.
- **AAA test structure** + descriptive names (`test_chat_service.py`) — normalization tests follow the same convention.

### Integration Points
- `ChatService.chat_stream()` at the `await tool.ainvoke(tool_call)` site — this is where the `str` result was previously received. After Phase 4.6, this receives `FlightSearchResult`; `ChatService` must call `.to_llm_summary()` for `ToolMessage` and `.model_dump_json()` for the SSE event.
- `ToolExecutionCard` `resultMetadata.full_result` field — currently a string rendered via ReactMarkdown. After Phase 4.6, frontend parses it as JSON and passes to native Chakra renderer.
- All import paths across the backend change when the flat layout becomes domain modules — the restructure wave must update every `from app.models import ...`, `from app.chat import ...`, `from app.tools.flight_search import ...`, etc.

<specifics>
## Specific Ideas

- The `segments[]` design is explicitly Amadeus-shaped (full-leg breakout, not stopover metadata). The ROADMAP calls out `developers.amadeus.com/self-service/category/flights` as the acceptance fixture source — the schema should map onto a real `FlightOffer` without lossy field collapses.
- Domain restructure target layout came from the FastAPI skill's domain-based project structure. User confirmed: `auth/`, `chat/`, `tools/` with per-domain files; `config.py` + `exceptions.py` at `app/` root; no `shared/` — `core/` only if genuinely needed.
- Migration is a distinct wave (pure refactor, no behaviour change) before the tool JSON contract changes. This is user-confirmed and should be Wave 1 in the plan.
- `to_llm_summary()` is the explicit seam for LLM narration — a method on `FlightSearchResult` that returns a compact human-readable text. The LLM never sees raw JSON.
- Native Chakra table/list rendering in `ToolExecutionCard` was explicitly chosen over keeping the ReactMarkdown path. The structured data path is the goal.

</specifics>
