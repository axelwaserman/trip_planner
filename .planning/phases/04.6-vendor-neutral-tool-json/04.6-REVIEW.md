# Phase 04.6: Code Review Report

**Reviewed:** 2026-05-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This phase adds a vendor-neutral `FlightSearchResult` model tree, normalizers for Amadeus and Skyscanner payloads, and a structured `FlightResultsTable` renderer in the frontend. The backend model design is sound; the Pydantic field constraints and the `PriceInfo.coerce_float_to_decimal` guard are correct. The test coverage on the happy path is good.

Two critical defects exist: the Skyscanner normalizer will crash with an `IndexError` on any input where `legs` is empty (contract not enforced), and `r.segments[0]` is accessed unconditionally in the frontend renderer even though `FlightResult.segments` is already constrained to `min_length=1` at the model level — a mismatch between backend guarantee and frontend trust. Five warnings cover logic issues and quality defects that will cause maintenance or runtime problems.

## Critical Issues

### CR-01: `normalize_skyscanner_itinerary` crashes with `IndexError` on empty `legs`

**File:** `backend/app/tools/flight_search.py:218`

**Issue:** `leg = itin["legs"][0]` raises `IndexError` when `itin["legs"]` is an empty list. There is no guard before this access. The Skyscanner itinerary contract does not guarantee non-empty `legs` in error responses, and `normalize_skyscanner_itinerary` has no unit test for this edge case. The `FlightResult` model requires `min_length=1` on `segments`, so passing an empty legs response into this path would also fail there — but the `IndexError` on line 218 fires before any Pydantic validation.

**Fix:**
```python
def normalize_skyscanner_itinerary(itin: dict[str, Any]) -> FlightResult:
    legs: list[dict[str, Any]] = itin.get("legs", [])
    if not legs:
        raise ValueError("Skyscanner itinerary has no legs; cannot normalize.")
    leg = legs[0]
    # ... rest unchanged
```

A corresponding test should be added:
```python
def test_skyscanner_empty_legs_raises() -> None:
    with pytest.raises(ValueError, match="no legs"):
        normalize_skyscanner_itinerary({"id": "x", "legs": [], "price": {"raw": 100.0, "currency": "USD"}})
```

### CR-02: `normalize_skyscanner_itinerary` produces a `FlightResult` with zero segments when `leg.segments` is empty — violating the `min_length=1` constraint at validation time, not at call time

**File:** `backend/app/tools/flight_search.py:227-228`

**Issue:** `leg_segments = leg.get("segments", [])` silently accepts an empty list. The function then calls `FlightResult(..., segments=segments, ...)` with an empty `segments` list. Pydantic's `min_length=1` constraint on `FlightResult.segments` (models.py:240) will raise a `ValidationError` at that point — not a graceful error. This is a silent logic error: the function appears to handle the missing-segments case (it uses `.get("segments", [])`) but does not guard against the downstream `ValidationError`. Callers that do not expect a `ValidationError` will receive an unhandled exception.

This is distinct from CR-01 (which crashes before even reaching `FlightResult` construction). Both edge cases share the same absent guard policy.

**Fix:**
```python
leg_segments: list[dict[str, Any]] = leg.get("segments", [])
if not leg_segments:
    raise ValueError(f"Skyscanner leg '{leg.get('id')}' has no segments; cannot normalize.")
```

## Warnings

### WR-01: Hardcoded stale date in tool docstring misleads the LLM

**File:** `backend/app/tools/flight_search.py:323`

**Issue:** The `search_flights` docstring contains `IMPORTANT: Today is November 13, 2025.` This string is injected verbatim into the LLM's tool description. As of the review date (2026-05-18) the date is more than six months stale. The LLM will use this date when resolving relative date references ("tomorrow", "next week"), producing incorrect results for end users. A hardcoded date in production code is a logic defect, not merely a style issue.

**Fix:** Either remove the hardcoded date entirely (the docstring already says "calculate based on TODAY'S DATE") or inject it dynamically at bind time:
```python
# In lifespan / ChatService init, after building the tool:
from datetime import date
search_flights.__doc__ = search_flights.__doc__.replace(
    "IMPORTANT: Today is November 13, 2025.",
    f"IMPORTANT: Today is {date.today().isoformat()}.",
)
```
A simpler approach: delete the `IMPORTANT: Today is…` sentence — the instruction to "calculate based on TODAY'S DATE" is sufficient and the LLM already knows the current date from context.

### WR-02: `normalize_skyscanner_itinerary` assigns `number_of_stops` from the leg level to every segment, not from per-segment data

**File:** `backend/app/tools/flight_search.py:261`

**Issue:** `number_of_stops=leg.get("stopCount", 0)` applies the leg's total stop count to each individual segment. For a multi-segment leg (e.g. two segments with one technical stop on the second segment), every segment will be tagged with the same stop count, which is incorrect. The Amadeus normalizer (line 183) reads `seg.get("numberOfStops", 0)` from the segment dict instead — the correct level. The Skyscanner fixture used in the unit test has only one segment with zero stops, so this bug is masked.

**Fix:**
```python
# Per-segment stop count from the segment dict (fall back to 0 if absent)
number_of_stops=seg.get("numberOfStops", leg.get("stopCount", 0)),
```
If the Skyscanner segment dict does not carry per-segment stop info, the fallback to `0` is more correct than propagating the leg-level count to every segment.

### WR-04: `MockLLM._astream` will raise `StopIteration` if called more times than there are pre-baked stream lists

**File:** `backend/tests/fixtures/llm.py:92`

**Issue:** `chunks: list[Chunk] = next(self._streams_iter)` raises `StopIteration` when the iterator is exhausted. Because `_astream` is an `async def` method, a `StopIteration` raised inside it is converted to a `RuntimeError: async generator raised StopIteration` by Python's async generator protocol (PEP 479). This is a test reliability defect: if a test incorrectly passes one fewer stream list than `chat_stream()` invocations expect, the error message is opaque and the failure mode is cryptic. The fix is a clear assertion.

**Fix:**
```python
async def _astream(self, ...) -> AsyncIterator[ChatGenerationChunk]:
    try:
        chunks: list[Chunk] = next(self._streams_iter)
    except StopIteration:
        raise RuntimeError(
            "MockLLM exhausted: more astream() calls were made than pre-baked stream lists. "
            "Add another inner list to the streams= argument."
        ) from None
    for chunk in chunks:
        ...
```

### WR-05: `test_amadeus_offer_normalizes_without_lossy_collapse` does not assert city field values, missing the key "no lossy collapse" guarantee for city lookup

**File:** `backend/tests/unit/test_tool_json_normalization.py:246-265`

**Issue:** The test is named `…_without_lossy_collapse` and the fixture provides a `AMADEUS_DICTIONARIES` with `"LAX": {"cityCode": "LA"}` and `"JFK": {"cityCode": "NYC"}`. The normalizer resolves these via `dictionaries["locations"].get(dep_iata, {}).get("cityCode", dep_iata)`. However, no assertion checks that `result.segments[0].departure.city == "LA"` or `result.segments[0].arrival.city == "NYC"`. The lossy-collapse scenario (where the city field would fall back to the IATA code instead of the resolved city name) is exactly what this test is supposed to catch, but it does not assert it.

**Fix:** Add assertions:
```python
assert result.segments[0].departure.city == "LA"   # resolved from dictionaries, not raw IATA
assert result.segments[0].arrival.city == "NYC"    # resolved from dictionaries, not raw IATA
```

### IN-03: `isFlightSearchResult` type guard in `ToolExecutionCard.tsx` does not check `v.results` element shape — a structurally valid but semantically wrong payload would render incorrectly

**File:** `frontend/src/components/ToolExecutionCard.tsx:26-36`

**Issue:** The guard checks `Array.isArray(v.results)` but does not verify that array elements have the `segments` field. `FlightResultsTable` accesses `r.segments[0]` (line 72) without a guard. If an API error returns a JSON object with `{status, results: [], count: 0, query: {...}}` the table renders fine (empty). But if `results` contains objects lacking `segments`, `r.segments[0]` will be `undefined` and `seg.departure.iata_code` will throw at runtime. The backend model enforces `min_length=1` on `segments`, so this only materializes if the frontend is called with unexpected data. The guard should be extended or `r.segments[0]` should be accessed safely.

**Fix (minimal):**
```tsx
const seg = r.segments[0]
if (!seg) return null  // guard against unexpected shape
```
Or extend `isFlightSearchResult` to check `v.results.every(r => Array.isArray(r?.segments) && r.segments.length > 0)`.
