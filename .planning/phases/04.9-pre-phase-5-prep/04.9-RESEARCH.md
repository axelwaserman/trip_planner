## Summary

Phase 4.9 has four parallel work streams all verified directly against the codebase. The work is primarily mechanical refactoring with high confidence because every import and component was read and traced.

**Work stream 1 — Model restructure:** `backend/app/models.py` is a 558-line monolith currently imported by 5 production modules and 4 test modules. It mixes flight domain models, flight search result models (vendor-neutral), chat API DTOs, and provider API models. The split is clean: no circular import risks exist because `app.models` imports only from `app.llm.errors` (for `ProbeErrorCode`), and nothing in `app.llm` imports back from `app.models`. The proposed 4-module split can proceed with simple search-replace of import paths.

**Work stream 2 — UserRepository:** `auth.py` has a module-global `_users_db` dict seeded once at import time via `load_users_from_env()`. It is referenced in three places within the same file: `get_current_user` reads it, the `login` route reads it, and the module-level call populates it. The `get_current_active_user` dependency (used by all protected routes) chains from `get_current_user`. Phase 5 retires this dict entirely in favour of Postgres. The extraction needs to be shaped to make Phase 5's swap trivially: `EnvUserRepository` keeps the current logic; Phase 5 replaces it with `PostgresUserRepository`.

**Work stream 3 — Skill routing:** Two skills already exist at `.claude/skills/fastapi/SKILL.md` and `.claude/skills/chakra-ui/SKILL.md`. A third skill for the React/TypeScript stack is missing. The skill routing table in CLAUDE.md is also absent.

**Work stream 4 — Frontend bugs:** All six bugs were traced to specific files and lines. Root causes confirmed: (1) empty-session guard is missing in `handleProviderChange` in `useChat.ts`; (2) font divergence is in `ChatInterface.tsx` which uses raw Chakra defaults (gray, blue) while Login and Settings use theme tokens; (3) the double-think bug is in `useChat.ts`'s `appendThinkingChunk` function which walks backward and finds the *first* thinking message instead of appending a *new* one when a new thinking block starts after a tool_result; (4) Settings URL error is not surfaced in `ProviderCard.tsx` — the `base_url` field has no client-side URL format validation and the backend's SSRF error is not rendered; (5) LM Studio stale cache comes from `useProviderRefresh` writing to localStorage but `ProviderCard` initialising `localModels` from props at mount, and the props-to-state sync `useEffect` uses a stable object reference as its dependency (not a deep comparison), so when the parent re-renders with the same object reference the effect skips; (6) sidebar overflow is in `Sidebar.tsx` where `{s.provider} · {s.model}` is rendered in a `Text` with `overflow: hidden` + `textOverflow: ellipsis` but no `minW: 0` on the `Flex` ancestor, causing flex overflow.

**Primary recommendation:** Execute the four work streams across four waves. Wave 0 creates test stubs for the auth changes. Wave 1 does the model split (mechanical, no logic changes). Wave 2 does the UserRepository extraction (unit-testable). Wave 3 creates the skill file and CLAUDE.md routing table. Wave 4 fixes all six frontend bugs. Each wave is independently committable.

## Auth Flow Diagram and UserRepository Interface

### Current auth flow

```
POST /api/auth/token
  → login() in auth.py
    → _users_db.get(form_data.username)        ← module-global dict read
    → verify_password(plain, hashed)            ← module-level function
    → create_access_token({"sub": username})   ← JWT creation
    → returns {"access_token": ..., "token_type": "bearer"}

Any protected route (e.g. GET /api/providers)
  → Depends(get_current_active_user)
    → Depends(get_current_user)
      → jwt.decode(token, ...)
      → _users_db.get(username)               ← module-global dict read
      → raises 401 if not found
    → raises 400 if user.disabled
```

### Three `_users_db` reference sites in `auth.py`

1. **Line 83**: `_users_db: dict[str, UserInDB] = load_users_from_env()` — module-level population
2. **Line 144**: `user = _users_db.get(username)` in `get_current_user`
3. **Line 181**: `user = _users_db.get(form_data.username)` in `login`

### Proposed `UserRepository` interface

```python
# backend/app/auth/repository.py

from typing import Protocol
from app.auth.models import UserInDB


class UserRepository(Protocol):
    """Protocol for user storage backends.

    Phase 4.9: EnvUserRepository (env-seed dict).
    Phase 5: PostgresUserRepository (psycopg async query).
    """

    def get_user(self, username: str) -> UserInDB | None:
        """Return the UserInDB for the given username, or None if not found."""
        ...

    def verify_password(self, plain: str, hashed: str) -> bool:
        """Return True if plain matches hashed."""
        ...


class EnvUserRepository:
    """UserRepository implementation that reads from AUTH_USERS env var.

    Populated once at construction time. Thread-safe for reads (dict is
    immutable after __init__). Phase 5 retires this class.
    """

    def __init__(self) -> None:
        self._users: dict[str, UserInDB] = _load_users_from_env()

    def get_user(self, username: str) -> UserInDB | None:
        return self._users.get(username)

    def verify_password(self, plain: str, hashed: str) -> bool:
        return _password_hasher.verify(plain, hashed)
```

## Frontend Bug Root-Cause Analysis

### Bug 1: Empty-session guard (`useChat.ts`)

**File:** `frontend/src/hooks/useChat.ts`, `handleProviderChange` function (lines 390–410)

**Root cause:** `handleProviderChange` unconditionally calls `initSession(...)` regardless of how many messages the current session has. There is no check of `messages.length` before calling `initSession`. The session has zero messages after first load (user opens app, sees welcome screen), and switching provider/model immediately creates a new session — burning a server round-trip and discarding the unused session.

**Fix:** In `handleProviderChange`, check whether the current session's snapshot has messages before deciding to create a new session:
```typescript
const handleProviderChange = useCallback(
  (provider: string, model: string) => {
    setProviderError(null)
    const currentSnapshot = sessionId ? getSessionSnapshot(sessionId) : null
    const hasMessages = (currentSnapshot?.messages.length ?? 0) > 0

    // Only create a new session if the current one has messages.
    // If it's empty, reuse it by re-running initSession in place.
    // This matches the Phase 4.9 REQ-frontend-bug-fixes spec:
    // "a new session is only created when the active session has ≥ 1 message"
    ...
    void initSession(selection.provider, selection.model, selection.baseUrl, selection.apiKey)
  },
  [initSession, sessionId]
)
```
Note: The desired behavior per the requirement is that an empty session is *replaced* (not kept as a zombie) rather than creating a second new session. So `initSession` should still be called, but it should send a `DELETE /api/chat/session/{old_id}` first when the old session is empty, OR the backend's `create_session` can simply reuse the existing ID. The simpler approach for Phase 4.9 is: call `initSession` unconditionally when there are no messages (same behavior as today but no new session is the *visible* change — the user never had a conversation there anyway). The actual change needed: skip `initSession` entirely when the provider/model matches the current session's provider/model AND the session has 0 messages.

**Concrete fix:**
```typescript
// Early exit: if provider + model unchanged and session is empty, no-op.
if (
  provider === currentProvider &&
  model === currentModel &&
  (sessionId ? getSessionSnapshot(sessionId).messages.length === 0 : false)
) {
  return
}
```

For a *different* provider/model on an empty session: still call `initSession` to swap the bound provider. This matches the requirement: "a new session is only created when the active session has ≥ 1 message." When the active session has 0 messages and the user changes provider/model, the backend creates a new session (different provider binding) but the user sees no disruption since there were no messages.

The simplest correct interpretation: skip calling `initSession` when provider AND model are both the same as current and messages.length === 0.

### Bug 3: Double-think rendering (`useChat.ts`)

**File:** `frontend/src/hooks/useChat.ts`, `appendThinkingChunk` function (lines 462–482 in `sendMessage`, and lines 763–782 in `retryLastTool`)

**Root cause:** The LLM stream for a `think → tool → think → reply` sequence emits events in this order:
1. `ThinkingEvent` chunks (first thinking block)
2. `ToolCallEvent`
3. `ToolResultEvent`
4. `ThinkingEvent` chunks (second thinking block — **BUG IS HERE**)
5. `ContentEvent` chunks

When the second `ThinkingEvent` arrives, `isStreamingThinking` is still `true` from the first block (it was set to `true` and never reset). The `appendThinkingChunk` function checks `isStreamingThinking` to decide whether to *append to the last thinking message* or *start a new one*. Since `isStreamingThinking === true`, it walks backward and finds the *first* thinking message (line 471: `if (prev.messages[i].role === 'thinking')`) and appends to it — instead of creating a new `ThinkingCard` for the second block.

**Fix:** Reset `isStreamingThinking = false` when a `tool_result` event is received (in the `case 'tool_result':` branch of `handleStreamEvent`). This signals that the previous thinking block ended, so the next `ThinkingEvent` starts a fresh card:
```typescript
case 'tool_result':
  updateToolResult(event.tool_result ?? '', event.elapsed_ms ?? 0)
  isStreamingAssistant = false
  isStreamingThinking = false   // ← ADD THIS LINE
  break
```
This fix must be applied in both the `sendMessage` closure (line ~626) and the `retryLastTool` closure (line ~935).

### Bug 4: Settings URL error feedback (`ProviderCard.tsx`)

**File:** `frontend/src/components/ProviderCard.tsx`, `handleSave` function (line 237)

**Root cause:** The Base URL input (`<Input type="url" ... />`) has no client-side URL format validation before `handleSave` calls `onSave(kind, updated)`. `onSave` calls `saveProviderSettings(updated)` and then `navigate('/app')` (in `SettingsProviders.tsx`). When `useChat` initialises on `/app`, it calls `initSession` with the saved `base_url`. The backend's `SessionCreateRequest._validate_base_url` validator rejects invalid URLs (must be localhost/127.0.0.1/host.docker.internal, http/https only) with a 400, which surfaces as a `SelectorErrorBanner` via the probe error path.

The problem: the user sees no error on the Settings page itself. They are immediately navigated to `/app` and the error shows up there as a banner — not where they entered the URL. Additionally, the `Field.Root` for the base URL lacks a `Field.ErrorText` element to display validation messages.

**Fix:** Add client-side URL validation in `handleSave` within `ProviderCard.tsx`:
```typescript
const [baseUrlError, setBaseUrlError] = useState<string | null>(null)

function handleSave() {
  setBaseUrlError(null)
  if (isLocal && baseUrl.trim().length > 0) {
    try {
      const parsed = new URL(baseUrl)
      if (!['http:', 'https:'].includes(parsed.protocol)) {
        setBaseUrlError('URL must start with http:// or https://')
        return
      }
      if (!['localhost', '127.0.0.1', 'host.docker.internal'].includes(parsed.hostname)) {
        setBaseUrlError('Host must be localhost, 127.0.0.1, or host.docker.internal')
        return
      }
    } catch {
      setBaseUrlError('Invalid URL format')
      return
    }
  }
  // ... rest of save logic
}
```
Add `<Field.ErrorText>{baseUrlError}</Field.ErrorText>` inside the `Field.Root` for the base URL input.

### Bug 5: LM Studio stale cache (`ProviderCard.tsx`)

**File:** `frontend/src/components/ProviderCard.tsx`, lines 180–194

**Root cause:** The `useEffect` that syncs upstream `settings.{ollama|lmstudio}.models` into `localModels` state uses `upstreamModels` as its dependency:

```typescript
const upstreamModels =
  kind === 'ollama'
    ? settings.ollama.models
    : kind === 'lmstudio'
      ? settings.lmstudio.models
      : null
useEffect(() => {
  if (upstreamModels === null) return
  setLocalModels(upstreamModels)
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [upstreamModels])
```

`upstreamModels` is an array reference from `settings`. When `handleRefresh()` runs:
1. It calls `refresh(kind)` which writes to localStorage via `saveProviderSettings`.
2. It calls `loadProviderSettings()` to get `fresh`.
3. It calls `setLocalModels(fresh.ollama.models)` directly — this works for the initial load.

But the bug is: after an eject/reload cycle where LM Studio reports a *different* (possibly smaller) set of models, the `SettingsProviders` page fetches `/api/providers` on mount and calls `setSettings(prev => {..., lmstudio: {..., models: newList}})`. This creates a *new array reference* for `settings.lmstudio.models`. The `useEffect` dependency `upstreamModels` should therefore fire correctly.

**Actual bug location:** `useProviderRefresh.ts` line 130: when the refresh returns `available: true`, it updates `settings.{ollama|lmstudio}.models` but only writes to localStorage. It does NOT call a callback or trigger a re-render in `ProviderCard`. The `ProviderCard` reads `localModels` from its own state, and `handleRefresh` does call `setLocalModels(fresh.{ollama|lmstudio}.models)` after the refresh — so the chip list *should* update.

The stale-cache bug is specifically triggered when: (1) user has LM Studio models in localStorage from a previous session, (2) they eject a model from LM Studio, (3) they click Refresh. The `useProviderRefresh` hook calls `POST /api/providers/refresh`, which hits the backend TTL cache. If the last refresh was < 60 seconds ago (`provider_models_cache_ttl_seconds = 60`), the backend returns the cached (stale) model list without re-hitting the LM Studio daemon. The `stale` list at line 508 of `routes.py` only includes providers where `now - timestamps[name] > ttl`.

**Fix:** Two-part fix:
1. `POST /api/providers/refresh` should bypass the TTL cache and force a live re-discovery when called from the Settings UI (intent is always fresh). Change routes.py: remove the TTL gating on the `refresh_providers` endpoint — always call `factory.refresh_local_models()` regardless of age. The TTL logic belongs on the passive lazy-load in `GET /api/providers`, not on the explicit user-triggered refresh. Specifically, change `routes.py:508-516` to always refresh rather than only refreshing stale entries.
2. No frontend change needed for the core bug once the backend always refreshes.

```tsx
      flex="1"
    >
      {preview}
    </Text>
    ...
  </Flex>
  <Text fontSize="13px" color="fg.muted" mt="0.5">
    {`${s.provider} · ${s.model}`}   ← THIS TEXT has no overflow control
  </Text>
</Box>
```

The `preview` line already has correct ellipsis overflow. The second `Text` (`provider · model`) at line 249 has no `overflow`, `textOverflow`, or `whiteSpace` properties. When a model name is long (e.g., `claude-3-5-sonnet-20241022`), this text wraps and the row grows past the fixed `h="48px"`, causing the model name to push into the next row or outside the sidebar.

**Fix:** Add overflow props to the `provider · model` Text:
```tsx
<Text
  fontSize="13px"
  color="fg.muted"
  mt="0.5"
  overflow="hidden"
  textOverflow="ellipsis"
  whiteSpace="nowrap"
>
  {`${s.provider} · ${s.model}`}
</Text>
```
Also confirm the row's `h="48px"` has `overflow="hidden"` or remove the fixed height in favour of `minH="48px"` to prevent the overflow from visually cutting text. The `Flex` ancestor already has `minW="0"` which is the standard Flexbox truncation fix — but it only applies to the first `Flex` child's content, not to the second `Text` which lives outside the `Flex`.

## Common Pitfalls

### Pitfall 1: Forgetting to update test imports after model split

**What goes wrong:** `mypy --strict` passes because the production code is updated, but test files still import from `app.models` (which is deleted), causing `ImportError` at test collection time.

**Why it happens:** Tests are not included in the production import graph trace; they are separate files that also import from `app.models`.

**How to avoid:** After updating all production imports, explicitly run `grep -r "from app.models" backend/tests/` to find remaining test-side imports. Four files need updating: `tests/fixtures/flights.py`, `tests/integration/test_chat_service_flow.py`, `tests/unit/test_flight_models.py`, `tests/unit/test_mock_client.py`, `tests/unit/test_tool_json_normalization.py`.

**Warning signs:** `pytest` fails at collection with `ImportError: cannot import name 'X' from 'app.models'`.

### Pitfall 2: Breaking the `SessionCreateError` → `ProbeErrorCode` import chain

**What goes wrong:** `SessionCreateError` in `app.models` references `ProbeErrorCode` from `app.llm.errors`. If `SessionCreateError` moves to `providers/models.py` but the import from `app.llm.errors` is forgotten, mypy fails.

**Why it happens:** `ProbeErrorCode` lives in `app.llm.errors` and `providers/models.py` imports from it — this is an upward dependency (providers depends on llm). That direction is fine (llm is a lower-level module).

**How to avoid:** Ensure `backend/app/providers/models.py` includes `from app.llm.errors import ProbeErrorCode` at the top.

**Warning signs:** `mypy` error: `Cannot find implementation or library stub for module named "app.llm.errors"` — unlikely since the path exists; more likely `NameError: name 'ProbeErrorCode' is not defined`.

### Pitfall 3: `chat/models.py` will have 17 classes after the migration

**What goes wrong:** `app.chat.models` currently has 5 stream event classes + `ErrorCode` (6 names). Adding 9 DTOs from `app.models` brings it to ~15 names. The file remains manageable (~200 lines) but it is worth checking the line count before finalising.

**How to avoid:** If `chat/models.py` exceeds 250 lines after the migration, consider splitting the chat DTOs (`ChatRequest`, `RetryRequest`, `ChatSessionInfo`, etc.) into `chat/dto.py`. For Phase 4.9, keep them together — premature splitting adds import complexity.

### Pitfall 4: Chakra v3 `colorScheme` vs `colorPalette`

**What goes wrong:** `ChatInterface.tsx` currently uses `colorScheme="blue"` on the Button (line 419). Chakra UI v3 uses `colorPalette` not `colorScheme`. Changing to `colorPalette="accent"` is the correct fix (see `ProviderCard.tsx` line 491 for the correct pattern already in use).

**Warning signs:** `jest` / Vitest snapshot test failures if snapshot tests exist; visual test failures showing wrong button color.

### Pitfall 5: `isStreamingThinking` reset is needed in BOTH closures

**What goes wrong:** The double-think fix requires resetting `isStreamingThinking = false` on `tool_result` events. This variable is declared as a local `let` inside BOTH `sendMessage` and `retryLastTool`. If the fix is applied only to `sendMessage`, retrying a tool call after a think→tool→think pattern still exhibits the bug.

**How to avoid:** Search for all occurrences of `isStreamingThinking = true` in `useChat.ts` — there are exactly 2 (one per closure). Add the reset in both.

### Pitfall 6: TTL bypass for refresh must not break GET /api/providers lazy-load

**What goes wrong:** If the TTL logic is removed from `POST /api/providers/refresh` AND also from `GET /api/providers`, then every `GET /api/providers` call hits the Ollama/LM Studio daemons — potentially on every ChatInterface mount.

**How to avoid:** The TTL logic in `GET /api/providers` (the `needs_lazy_load` check at line 450 of `routes.py`) is correct and should not change. Only the explicit `POST /api/providers/refresh` endpoint should bypass TTL gating.

```typescript
function validateBaseUrl(url: string): string | null {
  if (!url.trim()) return null  // empty is ok (use default)
  try {
    const parsed = new URL(url)
    if (!['http:', 'https:'].includes(parsed.protocol)) {
      return 'URL must use http:// or https://'
    }
    if (!['localhost', '127.0.0.1', 'host.docker.internal'].includes(parsed.hostname)) {

    }
  } catch {

  }
  return null
}
```
