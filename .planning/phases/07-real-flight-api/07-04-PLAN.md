<objective>
Land the gated real-API test suite (D-11 / D-12) and the supporting tooling: a `just test-duffel` runner, a CI job that runs only when both a secret and a repository variable are set, and a README section documenting Duffel signup → token creation → local + CI configuration. PR CI never requires the secret because the job is fully skipped when `vars.DUFFEL_E2E_ENABLED` is unset/false (D-11). The four tests mirror the proven Amadeus e2e suite shape minus the token-cache test (no token cache exists in the Duffel client).

Purpose: Without this plan, the real Duffel client has no live verification. With it, a developer with a Duffel sandbox account can run `just test-duffel` locally and CI can be flipped on by an admin via a single `vars.DUFFEL_E2E_ENABLED=true` toggle. PR runs remain unaffected.

Output: One e2e package directory with conftest + four-test module; one new method on `DuffelFlightClient` (`_auth_probe`); one justfile target; one CI job; one README section.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub `secrets.DUFFEL_API_TOKEN` → CI runner env | Token enters runner process via Actions secret expansion; passed to `uv run pytest` via `env:` block on the step. |
| CI runner → Duffel API | TLS-only; bearer in Authorization header; live network egress. |
| Local developer env → `_auth_probe` | Token leaves SecretStr at the construction site (Plan 07-03 wires this); local test runs hit Duffel sandbox directly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04-01 | Information Disclosure | bearer-token leakage in CI logs (uvicorn/pytest output, traceback echoes) | mitigate | `ApiKeyScrubber` (Plan 07-01) redacts `duffel_(test|live)_*` substrings in the application logging path; pytest output goes through stdout (not the scrubber), but tests do not log the token — they pass it via constructor. The bogus-token test (`test_error_mapping_401_with_bogus_token`) intentionally uses a NON-real synthetic token, so any leakage there is harmless. Real fixture-fed token never appears in test source. |
| T-07-04-02 | Information Disclosure | bearer token in committed test fixtures or YAML | mitigate | Plan 07-02 fixture audit (`grep -E 'duffel_(test|live)_[A-Za-z0-9_-]{20}'` returns 0 in JSON) carries forward; this plan adds CI YAML which uses `${{ secrets.DUFFEL_API_TOKEN }}` exclusively (no plaintext). README explicitly tells developers to put the token in `.env` (gitignored), not `.env.example`. |
| T-07-04-03 | Tampering | unauthorized PR using `secrets.DUFFEL_API_TOKEN` to exfiltrate token via test telemetry | accept | Default GitHub Actions behaviour: secrets are NOT exposed to PRs from forks. The `duffel-e2e` job runs only on the same-repo branch flow and is gated by `vars.DUFFEL_E2E_ENABLED`. PR CI from external contributors NEVER receives the secret. (Existing `e2e` job already operates under this same model.) |
| T-07-04-04 | Denial of Service | accidental rate-limit burn on Duffel sandbox via repeated CI runs | mitigate | Auth probe uses `GET /air/airlines?limit=1` (reference data — no per-search quota) per RESEARCH OQ-1. Live search tests issue exactly 4 requests per CI run. Pitfall 1 callout in README warns of sandbox sparsity, not quota exhaustion. |
| T-07-04-05 | Repudiation | CI silently green when DUFFEL_E2E_ENABLED unset, hiding regressions | accept | This is the intended default state — the var is opt-in for admins. PR CI should NEVER require Duffel; default-off means feature regressions caught only when an admin opts in or runs `just test-duffel` locally. Documented in README CI section. |
| T-07-04-06 | Tampering | invalid YAML in `.github/workflows/ci.yml` breaking ALL CI jobs | mitigate | YAML parse smoke test in Task 2 acceptance criteria (`python -c "import yaml; yaml.safe_load(...)"`). |
| T-07-04-SC | Tampering | npm/pip installs introducing untrusted code | accept | Phase 7 plans introduce zero new packages. `uv sync --frozen` in CI uses the locked `backend/uv.lock`. |
