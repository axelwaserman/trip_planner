# Phase 4.5: LLM Provider Abstraction (real cloud + dynamic Ollama) - Context

**Gathered:** 2026-05-16
**Status:** Ready for planning
**Worktree:** `.claude/worktrees/04.5-llm-provider-abstraction` (branch `phase/04.5-llm-provider-abstraction`)

<domain>
## Phase Boundary

Replace the singleton LangChain `BaseChatModel` that `ChatService` is constructed with at app startup with an `LLMProvider` Protocol. Build `OllamaProvider`, `LMStudioProvider`, `OpenAIProvider`, and `AnthropicProvider` implementations. `OllamaProvider` and `LMStudioProvider` discover their model list dynamically from the local daemon (no hard-coded model arrays). Cloud providers accept API keys from env or session payload. `LLMProviderFactory` builds a provider from session-scoped config; `ChatService.create_session()` calls the factory and stores the provider on session metadata so `chat_stream()` can use it.

Frontend shifts the provider/model selection out of the chat header and onto a dedicated `/settings/providers` page reachable from a new app-level sidebar. Multi-chat sidebar is introduced (active server-process sessions only — PG-backed persistence lands in Phase 5).

**In scope:**
- `app/llm/` package: `Protocol` + four provider implementations + factory.
- `LLMProvider.validate_config()` consolidates the 4.2 probe — `services/provider_probe.py` migrates onto the Protocol.
- `LLMProvider.list_models()` for local providers (Ollama, LM Studio); cache-until-Refresh.
- `POST /api/providers/refresh` to invalidate the discovery cache and re-enumerate.
- Optional `POST /api/providers/{id}/test` (live cloud key validation behind a Test-connection button).
- `ChatService` uses `app.state.llm_factory` instead of a bare bound `BaseChatModel`.
- Frontend: `/settings/providers` page (Local: Ollama + LM Studio with editable base URLs; Cloud: OpenAI + Anthropic with API key inputs); sidebar with chat list + "New chat" + Settings link; first-run CTA flow when no provider is configured.
- `localStorage` key `provider_settings` stores user-entered base URLs / API keys / selected models. Backend never persists keys.
- Per-real-cloud-provider happy-path acceptance test, gated on the corresponding `*_API_KEY` env var being set in the test environment (skipped in default PR CI).

**Out of scope (deferred):**
- Backend-stored encrypted API keys → Phase 5 (PG + KEK derivation).
- Mid-chat model switching → rejected as UX complexity; switching = new session.
- TTL-based discovery cache → not needed; Refresh button is the invalidation mechanism.
- PG-backed chat history list → sidebar shows in-memory sessions only in 4.5; Phase 5 makes it persistent.
- Profile page (travel tastes, preferred airlines, home airport, currency) → captured in `04.5-DEFERRED-PROFILE.md`; future phase.
- `LLMProvider` Protocol surface stability past Phase 6 (PydanticAI rework retires `bind_tools` from the Protocol — accepted rework).
- Cloud per-turn key rotation; auto-fallback to a different provider on failure; multi-device settings sync.

</domain>

<decisions>
## Implementation Decisions

### Provider Lifecycle & DI Shape

- **D-01: `ChatService` stays a singleton; provider object is built at `create_session` and stored on session metadata.**
  `create_session(provider, model, base_url=None, api_key=None)` calls `LLMProviderFactory.build(...)`, runs `provider.validate_config()`, calls `provider.bind_tools([search_flights])`, and stores the bound provider on `_metadata[session_id]` (or a parallel dict keyed by session id). `chat_stream(session_id)` reads the provider from there. `bind_tools()` runs once per session.

- **D-02: Provider/model is locked at session-create — no mid-chat switching.**
  Switching provider/model in the UI creates a new session. Conversation history stays coherent (every message generated by the same model). Frontend "+ New chat" picks up the user's current settings-page selection.

- **D-03: Lifespan no longer instantiates a default LLM directly.**
  `app.state.llm_factory = LLMProviderFactory(settings)` replaces the pre-built `init_chat_model(...)` call in `api/main.py::lifespan`. `ChatService` is constructed with the factory, not a `BaseChatModel`. The `MockFlightAPIClient` injection into `search_flights._flight_client` stays.

### Discovery & Refresh

- **D-04: Dynamic model discovery applies to local providers only (Ollama, LM Studio); cloud providers keep hard-coded curated model lists.**
  `OllamaProvider.list_models(base_url)` hits `GET /api/tags`. `LMStudioProvider.list_models(base_url)` hits `GET /v1/models`. Cloud providers return their static curated list (today's `Settings.get_available_providers()` shape preserved for them).

- **D-05: Discovery cache is in-memory, populated on first `GET /api/providers` after restart, invalidated only by the Refresh button.**
  Cache lives on `app.state` (e.g., `app.state.provider_models_cache: dict[str, list[str]]`). No TTL. Implication accepted: a user who pulls a new model in Ollama and forgets to click Refresh won't see it until they do.

- **D-06: Single global "Refresh models" button on the settings page; backend exposes `POST /api/providers/refresh`.**
  Backend re-discovers all *available local* providers in parallel (asyncio.gather), updates the cache, returns the fresh enumeration. Cloud providers are no-ops. UI: one button at the top of the settings page (per-provider Refresh rejected as unnecessary).

- **D-07: `list_models` lives on the `LLMProvider` Protocol, not on the probe service.**
  Each provider class owns its discovery. The Protocol grows a `list_models` member. Phase 6 PydanticAI rework cost is accepted (already accepted for `bind_tools`).

### API Keys

- **D-08: Session-payload key wins; env-var key is the fallback when no payload key is present.**
  Settings page is the authoritative source. `LLMProviderFactory.build(provider, model, api_key=payload_key)` uses `payload_key or settings.{provider}_api_key`.

- **D-09: API keys are captured once in the `POST /api/chat/session` payload, held on session metadata in process memory, never logged, never persisted to disk.**
  Dies with the session. The settings page stores the key in `localStorage` (`provider_settings`) on the frontend; backend never writes it anywhere.

- **D-10: Logs scrub fields named `api_key` / `*_api_key` and string patterns matching `sk-...` / `sk-ant-...`.**
  Minimal scrubber lands in 4.5 so the system is correct from day one. Phase 8's `structlog` migration formalizes processor-based scrubbing.

- **D-11: Backend-stored encrypted API keys are the target end-state, deferred to Phase 5 (PG).**
  Captured here so the migration is on the radar. Phase 5 plan must specify a KEK-derivation story (env-derived OK for v1.5; real KMS post-v1).

### `validate_config` & Test Connection

- **D-12: `LLMProvider.validate_config()` IS the probe — `services/provider_probe.py` migrates onto the Protocol.**
  The 4.2 free-standing `probe_provider()` becomes per-provider `validate_config()`. `ProbeError` and `ProbeErrorCode` types stay (they're the existing wire contract; routes.py + frontend `mapProbeError` consume them) — they relocate to a shared module (e.g., `app/llm/errors.py`). The old `services/provider_probe.py` either becomes a thin backwards-compat wrapper or is deleted in 4.5; planner picks based on test impact.

- **D-13: Default `validate_config()` behavior:**
  - **OllamaProvider / LMStudioProvider:** static (base_url parseable) + liveness probe (`/api/tags` or `/v1/models`) + selected-model presence check. Returns `provider_unreachable` / `model_not_installed`.
  - **OpenAIProvider / AnthropicProvider:** key presence only (env or payload). Returns `missing_api_key` if neither source has a key. **No outbound API call by default** — preserves today's session-create UX (no surprise billing on every new chat).

- **D-14: Live cloud key validation is a separate, opt-in code path triggered by a "Test connection" button on the settings page.**
  New backend endpoint `POST /api/providers/{provider}/test` performs a 1-token call:
  - OpenAI: `GET /v1/models` (cheap, no token cost).
  - Anthropic: `POST /v1/messages` with `max_tokens: 1` and a single-character message.
  Returns success or a structured error. New `ProbeErrorCode` value (e.g., `INVALID_API_KEY`) added; the F-taxonomy from 4.2 grows by one bucket.

### LM Studio Integration

- **D-15: `LMStudioProvider` is a first-class, distinct provider class.**
  Sits next to `OllamaProvider`, `OpenAIProvider`, `AnthropicProvider`. Default `base_url=http://localhost:1234/v1` (editable on the settings card).

- **D-16: Internal implementation may delegate to `langchain-openai`'s `ChatOpenAI` with a custom `base_url` and a sentinel `api_key="lm-studio"`.**
  LM Studio's REST surface is OpenAI-compatible. The SDK requires a non-empty `api_key` field even when the local server doesn't enforce auth — a sentinel value satisfies the validator without representing a real secret. Planner confirms the sentinel approach during research; an alternative is to use the OpenAI SDK directly under a thin wrapper.

- **D-17: LM Studio requires no API key in v1.**
  Local trust model, identical to Ollama. The settings card shows base URL, model dropdown, and Refresh — no key input.

- **D-18: LM Studio discovery via `GET /v1/models`.**
  Same Refresh contract as Ollama. `validate_config()` checks `/v1/models` for liveness and that the selected model id is in the response.

### Frontend Navigation Shape

- **D-19: New `/settings/providers` page reachable from an app-level sidebar.**
  Sidebar contains: chat list ("active sessions" in 4.5 — see D-22), "+ New chat" button, "Settings" link. Sidebar is collapsible.

- **D-20: Login flow lands on `/` (the chat surface), not on settings.**
  Backend `GET /api/providers` returns currently-available providers/models. Frontend logic on `/`:
  - At least one provider configured + at least one model available → empty chat shell, ready for input.
  - No provider configured / no model available → empty-state CTA "Configure a provider to get started" with a link to `/settings/providers`.

- **D-21: `localStorage` key `provider_settings` shape (snake_case keys, mirrors existing `llm_provider_config` casing):**
  ```ts
  {
    selected: { provider: "ollama" | "lmstudio" | "openai" | "anthropic", model: string },
    ollama: { base_url: string, models: string[] },          // models = last discovered list
    lmstudio: { base_url: string, models: string[] },
    openai: { api_key: string, model: string },
    anthropic: { api_key: string, model: string }
  }
  ```
  The existing `llm_provider_config` localStorage key from Phase 4.1/4.2 is migrated/replaced — planner specifies the migration step. `auth_token` (from 4.2) stays separate.

- **D-22: Sidebar's chat list in 4.5 = "active server-process sessions" only.**
  Backed by `ChatService._histories.keys()`. Backend exposes a `GET /api/chat/sessions` endpoint listing the current user's active sessions; entries die on backend restart. UI labels this honestly (e.g., "Recent chats" with a subtle indicator that they're not persistent yet) — no "all your chats forever" promise. Phase 5 wires this to PG and the sidebar becomes durable.

- **D-23: Per-session badge in the chat surface shows the active provider/model.**
  Visible at all times so the user knows which model is generating the current conversation. Replaces the in-header dropdown.

### Backend route additions / changes

- **D-24: `POST /api/chat/session` payload shape extends to:**
  ```json
  {
    "provider": "ollama" | "lmstudio" | "openai" | "anthropic",
    "model": "string",
    "base_url": "string | null",   // local providers only
    "api_key":  "string | null"    // cloud providers only; D-08 precedence
  }
  ```
  Existing 4.2 contract (provider + model only) is the subset case — `base_url` and `api_key` default to None and the factory falls back to `Settings`.

- **D-25: `GET /api/providers` returns the same shape as today, but enriched:**
  - Ollama / LM Studio entries' `models` field comes from the discovery cache.
  - Each entry adds `base_url` (from settings or default) so the settings page can pre-fill.
  - `available` flag remains. For local providers, `available` becomes "did the last discovery attempt succeed" — adjusted by Refresh.

- **D-26: `POST /api/providers/refresh` and `POST /api/providers/{provider}/test` are new endpoints.**
  Both protected by `get_current_active_user`. Both return structured success/error bodies that map to `ProbeError` shape.

- **D-27: `GET /api/chat/sessions` is the new sidebar-feeding endpoint.**
  Returns active session ids + their `created_at` + provider/model badge. Uses the existing `ChatService._histories` keys + `_metadata`. Protected route.

### Configuration (`Settings`)

- **D-28: New `Settings` fields:**
  - `lmstudio_base_url: str = "http://localhost:1234/v1"` (mirrors `ollama_base_url`).
  - No `lmstudio_api_key` field (D-17).
  - `provider_probe_timeout_seconds` from 4.2 stays; new local providers reuse it.
- Cloud `*_model` defaults stay as fallback when the user hasn't selected one.

### Claude's Discretion

- File layout under `backend/app/llm/`: `protocol.py` (`LLMProvider` Protocol), `factory.py` (`LLMProviderFactory`), `providers/{ollama,lmstudio,openai,anthropic}.py`, `errors.py` (relocated `ProbeError` / `ProbeErrorCode`). Researcher confirms naming.
- Whether `validate_config` returns `ProbeError | None` or raises a typed exception consumed by the route layer — implementation choice.
- Whether `LMStudioProvider` wraps `ChatOpenAI` directly or uses the `openai` SDK + a custom `BaseChatModel` shim.
- Frontend file layout under `frontend/src/`: `pages/SettingsProviders.tsx`, `components/Sidebar.tsx`, `components/ProviderCard.tsx`, etc. — conform to existing layout (`pages/Login.tsx`, `components/`).
- Whether the discovery cache lives on `app.state` directly or behind a small `ProviderRegistry` service object.
- Whether `provider_settings` migration from `llm_provider_config` is one-shot read-and-overwrite or runs on every settings-page load.

</decisions>

### Anti-patterns to avoid (from 04.2-LEARNINGS.md context)

- **Don't smuggle API keys through query strings or path params.** Keys travel only in JSON request bodies. Logs scrub them.
