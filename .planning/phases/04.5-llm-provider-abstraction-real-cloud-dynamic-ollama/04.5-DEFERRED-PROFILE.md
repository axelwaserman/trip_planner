# Deferred: User Profile Page (Travel Tastes & Preferences)

> **Status:** Captured during Phase 4.5 discussion as a future-phase idea.
> Not in scope for 4.5; not yet roadmapped.

**Captured:** 2026-05-16
**Source:** Phase 4.5 discuss-phase
**Originator:** User (during Area 1 discussion of post-login UX)

---

## The Idea

Phase 4.5 introduces a `/settings/providers` page reachable from a sidebar (alongside the chat list and the "+ New chat" button). The same sidebar Settings link should eventually expose a **user profile page** for travel-domain personalization.

**Examples of what would live there:**
- Preferred home airport(s) — IATA code(s) used as default origin.
- Travel tastes — class preference (economy / premium / business), airline allow- and block-lists, layover tolerance, redeye comfort, time-of-day window preferences.
- Currency preference — drives `price.currency` formatting and possibly conversion in the tool result.
- Trip-type defaults — solo / family / business; default passenger count.
- Loyalty programs — frequent-flyer numbers, status tier (drives upgrade-aware suggestions later).
- Saved searches / "watch this route" alerts.

## Why this is its own phase

Profile data is **persistent, per-user, and structured** — it requires:

- A `user_preferences` (or similar) table in Postgres → Phase 5 territory.
- A schema migration with stable field names (no value in shipping a localStorage-backed v0 that gets thrown away).
- Tool integration: the agent must actually consume preferences to be useful. That's a meaningful agent-behavior change (default-origin handling, preference-aware ranking) and warrants its own design pass.

Doing it in Phase 4.5 would:
- Force preference data into localStorage (lost on device change, no source of truth).
- Add tool/agent changes the LangChain → PydanticAI migration (Phase 6) would re-touch.
- Compete for design attention with the provider-abstraction work that 4.5 actually has to ship.

## When to schedule it

**Earliest viable phase:** post-Phase 5 (Postgres available) and post-Phase 6 (PydanticAI agent surface stable so preference-aware tool-arg defaults are clean).

**Plausible phase numbering:** "Phase 9" (post-v1 feature work) or as part of a v1.5 / v2 milestone block. Defer the exact slotting to roadmap planning.

**Dependencies:**
- Phase 5: PG + `User` table + auth re-platform.
- Phase 6: PydanticAI `Agent` shape stable; tool argument defaults can be cleanly populated from user context.
- Phase 4.6: vendor-neutral tool JSON shape locked in; preference-aware ranking has a stable target schema.

## Surface changes when it lands

**Backend:**
- New `user_preferences` table (or extend `users` row with a JSON `preferences` column).
- New `GET /api/me/preferences` and `PATCH /api/me/preferences` endpoints.
- `search_flights` tool gains optional preference-context inputs (or `ChatService` injects them into the system prompt).

**Frontend:**
- New `/settings/profile` page (reachable from the same sidebar Settings link → profile vs. providers tab structure).
- Preference form using the same Chakra v3 `Field.Root` pattern as the providers settings page.
- Sidebar "Settings" link possibly expands to a sub-nav (Providers / Profile / Account).

## Linkage to 4.5

Nothing in 4.5 should preclude this:

- The `/settings/providers` page should be reachable via a route that allows adding sibling routes (e.g., `/settings/profile` later) — the planner should structure the route hierarchy so a sub-nav is a small lift, not a rebuild.
- localStorage namespace `provider_settings` is provider-specific, not a "user preferences" catch-all — keep it separate from a future `user_profile` namespace so they don't collide.
- The Settings link in the sidebar can land on `/settings/providers` as the only tab in 4.5; future phases add sibling tabs without renaming the link.

## Reminder

If during Phase 5 or 6 planning we realize a preference-aware tool call would be a quick win, surface this doc and decide whether to lift the profile work forward. Otherwise, leave it for a dedicated phase that gets its own discuss-phase pass.
