## Provider Lifecycle & DI Shape

User initially asked for tradeoffs of "model locked at session-create, no mid-chat switching" before answering. Analysis presented covering wins (single bind_tools, coherent history, simpler key handling) and costs (frontend contract change, can't pick up newly-pulled Ollama models mid-session, no cost-arbitrage UX).

User then introduced a UX upgrade: dedicated `/settings/providers` page after login + sidebar with chat list + "+ New chat" + Settings link. Claude responded with a tension analysis (what fits Phase 4.5 vs. what needs Phase 5 PG persistence), a recommended v1 cut, and a flagged decision on the post-login landing page. User confirmed (a) "login → chat → backend checks for available providers → CTA if none configured."

### How ChatService consumes the provider

| Option | Description | Selected |
|--------|-------------|----------|
| Per-session provider, cached on the session | Singleton ChatService stays. Provider built at create_session, stored on session metadata, bind_tools runs once per session. | ✓ |
| Provider built fresh per chat_stream() call | Provider rebuilt every turn from session metadata. Most flexible, slowest. | |
| ChatService becomes per-session | Lifespan no longer builds singleton; built per-request. Biggest architectural change. | |

### Mid-chat model switching

| Option | Description | Selected |
|--------|-------------|----------|
| Locked at session-create (switch = new session) | Conversation stays coherent under one model. Bind_tools runs once. | ✓ |
| Per-turn provider override allowed | User can switch mid-conversation via header dropdown; history mixes model output. | |

### Frontend navigation shape

| Option | Description | Selected |
|--------|-------------|----------|
| Settings as a destination + sidebar with chat list + "+ New chat" + Settings link | Standard chat-app shape (Claude.ai, ChatGPT). Login → `/` chat surface; CTA when no provider configured. | ✓ |
| Settings-first (force users through `/settings` after login) | First-run friendly but annoying for returning users. | |
| Keep dropdown in chat header | Status quo; reproduces today's broken-ish UX with a richer surface. | |

**User's choice:** Singleton ChatService + per-session provider on metadata + locked at session-create + new sidebar / settings page architecture.
**Notes:** Multi-chat sidebar in 4.5 = "active server-process sessions only" — Phase 5 (PG) makes the chat list durable. Profile page / travel tastes captured in `04.5-DEFERRED-PROFILE.md`. Login lands on `/` (chat); empty-state CTA links to `/settings/providers` if no provider configured.

## Discovery & Refresh

### Discovery trigger

| Option | Description | Selected |
|--------|-------------|----------|
| On every GET /api/providers + on Refresh | No backend cache. Always fresh. ~50-200ms per call. | |
| Cached with TTL + Refresh bypasses | TTL (e.g., 60s) + `?fresh=true` on Refresh. Cache invalidation logic for negligible gain. | |
| Only on Refresh + on first load after restart | In-memory cache, no TTL, invalidated by Refresh button. | ✓ |

### Code location

| Option | Description | Selected |
|--------|-------------|----------|
| New `app/services/provider_registry.py` | Service module separate from probe. | |
| Extend `app/services/provider_probe.py` | Add list_models alongside probe_provider. Tighter coupling. | |
| On the Provider class itself | `OllamaProvider.list_models()` / `LMStudioProvider.list_models()`. Each provider owns its discovery. Protocol grows a member. | ✓ |

### Refresh scope

| Option | Description | Selected |
|--------|-------------|----------|
| Per-provider Refresh button on each provider card | Faster, more targeted; more UI controls. | |
| Global Refresh (one button, refreshes all) | Single button at top of settings page; parallel discovery. | ✓ |

**User's choice:** Cache-until-Refresh + on-Provider-class discovery + global Refresh button.
**Notes:** Cloud providers keep curated model lists (no discovery). Implication accepted: pulling a new Ollama model requires hitting Refresh to see it.

## API Key Precedence & Handling

### Precedence when both env-var and session-payload key are set

| Option | Description | Selected |
|--------|-------------|----------|
| Session payload wins (env is fallback) | User-supplied key takes precedence. Matches "I just typed it, use it" intuition. | ✓ |
| Env wins (payload is fallback) | Env always wins; UI key silently ignored when env set. Counterintuitive. | |
| Reject if both set (400) | Forces explicit choice; most annoying. | |

### Wire / log handling

| Option | Description | Selected |
|--------|-------------|----------|
| Captured at session-create, held on session in-memory, never logged | Key arrives once via POST /api/chat/session; dies with session; logs scrub `*_api_key` and `sk-...` patterns. | ✓ (v1) |
| Per-turn (every chat request re-sends the key) | Avoids server-side persistence but inflates request size and reruns bind_tools. | |
| Backend-side encrypted store | Persists across restart; needs PG + KEK. | ✓ (target, deferred to Phase 5) |

**User's choice:** Session-payload precedence + capture-once / session-lived storage in v1; encrypted backend store is the Phase 5 target.
**Notes:** Minimal log scrubber lands in 4.5 so the system is correct from day one. Phase 8's `structlog` work formalizes processor-based scrubbing. KEK derivation story is Phase 5's planning concern.

## validate_config Scope vs. Existing Probe

### What does validate_config do, and how does it relate to 4.2's probe?

| Option | Description | Selected |
|--------|-------------|----------|
| validate_config IS the probe — move probe logic onto the Protocol | Per-provider classes own liveness/key check. provider_probe.py either becomes a thin wrapper or is deleted. ProbeError types relocate. | ✓ |
| validate_config is config-only; probe stays for liveness | Two layers, two error surfaces. validate_config runs at settings-save; probe runs at session-create. | |
| validate_config = config + live key validation | Static config + 1-token API call to verify cloud keys. Strong guarantee, surprise billing risk. | |

### Live cloud validation timing

| Option | Description | Selected |
|--------|-------------|----------|
| Skip live validation in v1 — env-presence-only | Fastest UX, no surprise billing. | |
| Live, only when user clicks "Test connection" on settings page | New endpoint `POST /api/providers/{provider}/test`. User opts in. | ✓ |
| Live, automatic on every session-create | Catches revoked keys earliest; ~1s added to every chat-start. | |

**User's choice:** validate_config IS the probe + live validation only via opt-in "Test connection" button.
**Notes:** Default validate_config behavior stays cheap (no outbound cloud call). New ProbeErrorCode value (e.g., `INVALID_API_KEY`) added for the test path. Existing F1-F3 error taxonomy from 4.2 grows by one bucket.

## LM Studio Integration Shape

### Provider class shape

| Option | Description | Selected |
|--------|-------------|----------|
| Distinct `LMStudioProvider` class | First-class, next to Ollama/OpenAI/Anthropic. Default base_url=http://localhost:1234/v1. May internally use ChatOpenAI. | ✓ |
| OpenAI provider with editable base_url | Single OpenAIProvider; user types localhost:1234 to point at LM Studio. Less code; bad UX. | |
| Generic OpenAICompatibleProvider with named presets | One class accepts {presetName, base_url, api_key}. Future-extends to vLLM, Together, Groq. Gold-plating for v1. | |

### LM Studio API key

| Option | Description | Selected |
|--------|-------------|----------|
| No API key required (local trust) | Same trust model as Ollama. Sentinel `Bearer lm-studio` to satisfy SDK. | ✓ |
| Optional API key field | Slight UI complexity for a corner case. | |

**User's choice:** Distinct LMStudioProvider class + no API key in v1.
**Notes:** Internal implementation likely wraps `langchain-openai` `ChatOpenAI` with `base_url=http://localhost:1234/v1` + sentinel `api_key="lm-studio"`. Discovery via `GET /v1/models`. validate_config liveness probe + selected-model presence check, identical contract to Ollama.
