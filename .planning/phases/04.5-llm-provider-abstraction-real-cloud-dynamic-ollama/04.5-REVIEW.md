# Phase 04.5: Code Review Report

**Reviewed:** 2026-05-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 50
**Status:** issues_found

## Summary

Phase 4.5 ships an LLM-provider Protocol layer, a per-app factory, four concrete
providers (Ollama / OpenAI / Anthropic / LM Studio), an API-key log scrubber,
three new endpoints, per-user session partitioning in `_metadata`, and a
settings UI.

The Protocol surface, factory dispatch, key-precedence wiring, and provider
probes are clean and well-tested. The new `POST /api/providers/refresh`,
`POST /api/providers/{provider}/test`, and `GET /api/chat/sessions` endpoints
all carry `Depends(get_current_active_user)` and pass their respective
auth-required tests. The SSRF allowlist on `SessionCreateRequest.base_url` is
correct (http/https + {localhost, 127.0.0.1, host.docker.internal}) and the
api_key field has the expected length cap + whitespace stripping.

The phase has, however, shipped **multiple high-impact authorization gaps and
a wire-shape mismatch** that escaped the test suite because the tests
themselves encode the buggy contract:

1. `DELETE /api/chat/session/{session_id}` carries **no authentication and no
   ownership check** — any unauthenticated caller can delete any user's
   session by guessing/learning the UUID. The phase's own session-partitioning
   work (D-22, D-27) was undone here.
2. `POST /api/chat` requires auth but never verifies the `session_id` in the
   request body belongs to `current_user`. Alice with a valid token can post
   to / read the SSE stream of Bob's session if she learns the UUID — a
   horizontal privilege escalation.
3. The frontend `useSessions` hook reads `id` and `last_message_preview` but
   the backend `ChatSessionInfo` emits `session_id` and `first_message_preview`.
   The Sidebar will route to `/app?session=undefined` and render every chat
   row's preview text as the placeholder `"New chat"`.
4. The OpenAI key-shape regex in the log scrubber does not match production
   `sk-proj-*` / `sk-svcacct-*` formats — those keys will leak through any
   `print()` / log line that happens to include them.
5. The chat-stream catch-all echoes raw `str(e)` over the SSE wire, leaking
   internal exception text (provider URLs, library stack info) to the client.

The structural Protocol work and the cloud test endpoint are otherwise solid.
All findings below carry concrete fixes; the BLOCKER-tier items are
auth/secret-handling regressions that should be patched before this phase
ships.

## Critical Issues

### CR-01: `DELETE /api/chat/session/{session_id}` has no auth and no ownership check

**Status:** ✓ Fixed in commit a2bddee
**File:** `backend/app/api/routes/routes.py:230-263`
**Issue:** The handler signature is

```python
async def delete_session(
    session_id: str,
    chat_service: Annotated[ChatService, Depends(get_chat_service)],
) -> None:
```

— no `Depends(get_current_active_user)`, no comparison against
`metadata["user_id"]`. Any unauthenticated caller can issue
`DELETE /api/chat/session/<known-uuid>` and erase another user's session
plus chat history (`_histories`, `_metadata`, `_bound_providers`,
`_last_activity`). The phase's own integration test
(`backend/tests/integration/test_session.py:28`) passes precisely because
no auth header is sent — the test cements the bug.

This wipes the entire premise of the D-22/D-27 partitioning work (a user can
own a session list, but anyone can delete entries from it).

**Fix:**

```python
@router.delete("/api/chat/session/{session_id}", status_code=status.HTTP_204_NO_CONTENT)
async def delete_session(
    session_id: str,
    chat_service: Annotated[ChatService, Depends(get_chat_service)],
    current_user: Annotated[User, Depends(get_current_active_user)],
) -> None:
    metadata = chat_service._metadata.get(session_id)
    if metadata is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND,
                            detail=f"Session {session_id} not found")
    if metadata.get("user_id") != current_user.username:
        # Same shape as 404 to avoid leaking session existence to non-owners.
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND,
                            detail=f"Session {session_id} not found")
    chat_service._histories.pop(session_id, None)
    chat_service._metadata.pop(session_id, None)
    chat_service._bound_providers.pop(session_id, None)
    chat_service._last_activity.pop(session_id, None)
```

Update `backend/tests/integration/test_session.py` to send `auth_headers`
on every `client.delete(...)` call and add a regression test that proves
user-A's token cannot delete user-B's session (must return 404, not 204).

### CR-02: `POST /api/chat` does not enforce session ownership

**Status:** ✓ Fixed in commit 7d8e1e5
**File:** `backend/app/api/routes/routes.py:50-108`
**Issue:** The chat route requires a JWT (`_current_user`) but never compares
`request.session_id` against `chat_service._metadata[session_id]["user_id"]`
before streaming. With a valid user-A token, Alice can issue
`POST /api/chat {"session_id": "<bob-session-uuid>", "message": "..."}`
and:

1. Read every prior message in Bob's history through the SSE stream
   (LangChain replays history into the model context).
2. Append messages to Bob's history (`history.add_user_message(message)` in
   `chat.py:281`).
3. Have the LLM invoke `search_flights` on Bob's session with Alice's prompt.

This is a horizontal privilege escalation: knowing a session UUID is enough
to hijack any user's chat. The session UUID gets returned to the browser
and is visible in network traces, browser history, etc.

**Fix:** Reject mismatches at the route boundary, with the same
not-found-shape as a missing session to avoid leaking existence:

```python
async def chat(
    request: ChatRequest,
    chat_service: Annotated[ChatService, Depends(get_chat_service)],
    current_user: Annotated[User, Depends(get_current_active_user)],
) -> StreamingResponse:
    metadata = chat_service._metadata.get(request.session_id)
    if metadata is None or metadata.get("user_id") != current_user.username:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Session {request.session_id} not found",
        )
    # ... rest unchanged
```

Add an integration test: alice creates a session, bob (different token) tries
`POST /api/chat` with alice's session_id; assert 404.

### CR-03: Frontend session-list field names do not match backend response

**Status:** ✓ Fixed in commit ae13fad
**File:** `frontend/src/hooks/useSessions.ts:22-28`,
`frontend/src/components/Sidebar.tsx:135-170`
**Issue:** Backend `ChatSessionInfo` (`backend/app/models.py:317-327`) emits
`session_id` and `first_message_preview`. Frontend `ChatSession` interface
declares:

```ts
export interface ChatSession {
  id: string                       // backend sends "session_id"
  created_at: string
  provider: string
  model: string
  last_message_preview?: string    // backend sends "first_message_preview"
}
```

`useSessions` does **not** transform the payload — it just stuffs
`body.sessions` straight into state, so every row in the Sidebar reads
`s.id` (always `undefined`) and `s.last_message_preview` (always
`undefined`). Effects:

- `handleSessionClick(s.id)` navigates to `/app?session=undefined` for every
  row.
- The `key={s.id}` collisions in `Stack` produce React duplicate-key warnings
  in dev and undefined behaviour with strict mode.
- The preview falls through to the literal placeholder `'New chat'` for every
  session because `s.last_message_preview` is always falsy.
- The `useSessions.test.ts` and `Sidebar.test.tsx` specs all use the wrong
  fake shape (`id`, `last_message_preview`) so the unit tests are green but
  the production wire contract is broken.

**Fix:** Pick one canonical shape and align both ends. Cheapest is to
align the frontend with the existing backend wire (no migration needed):

```ts
export interface ChatSession {
  session_id: string
  created_at: string
  provider: string
  model: string
  first_message_preview?: string
}
```

Then update `Sidebar.tsx` to read `s.session_id` and
`s.first_message_preview`, and update `useSessions.test.ts` +
`Sidebar.test.tsx` fixtures to use the wire-correct field names. Add an
integration test that boots the backend (or just the route) and asserts the
frontend type compiles against the actual response keys.

### CR-04: Log scrubber regex does not match modern OpenAI key formats (`sk-proj-*`, `sk-svcacct-*`)

**Status:** Fixed (commit pending)
**File:** `backend/app/llm/log_scrubbing.py:27-31`
**Issue:** The patterns are:

```python
SECRET_PATTERNS = (
    (re.compile(r"sk-ant-[A-Za-z0-9_-]{20,}"), "sk-ant-[REDACTED]"),
    (re.compile(r"sk-[A-Za-z0-9]{20,}"),       "sk-[REDACTED]"),
    (re.compile(r'("[A-Za-z0-9_]*api_key"\s*:\s*)"[^"]+"'), r'\1"[REDACTED]"'),
)
```

The bare `sk-` regex requires **20+ alphanumeric** chars immediately after
`sk-`. OpenAI's project-scoped keys have the prefix `sk-proj-` and
service-account keys have the prefix `sk-svcacct-` — both contain a `-`
character within the first 8 characters, which terminates the
`[A-Za-z0-9]{20,}` match. A real key like
`sk-proj-AbCdEfGhIjKlMnOpQrStUvWxYz0123` will match **zero characters**
because there are only 4 alphanumeric chars (`proj`) before the next `-`.

Result: any OpenAI project-scoped or service-account key that ends up in a
log line — through `print()`, `repr()`, an exception traceback, or any
third-party logger that emits the key — will be logged in clear. This
defeats D-10's stated guarantee that "API keys never reach a log handler".

The unit test suite has no `sk-proj-` or `sk-svcacct-` case, so this is
silently uncovered.

**Fix:** Allow `[A-Za-z0-9_-]` and lower the run length, matching the
Anthropic pattern's tolerance:

```python
SECRET_PATTERNS = (
    (re.compile(r"sk-ant-[A-Za-z0-9_-]{20,}"),  "sk-ant-[REDACTED]"),
    (re.compile(r"sk-(?:proj-|svcacct-|admin-|user-)?[A-Za-z0-9_-]{20,}"),
                                                "sk-[REDACTED]"),
    (re.compile(r'("[A-Za-z0-9_]*api_key"\s*:\s*)"[^"]+"'), r'\1"[REDACTED]"'),
)
```

Add unit tests for `sk-proj-...` and `sk-svcacct-...` formats, plus the
Anthropic-precedes-OpenAI ordering test for the new shapes. Verify the new
bare-`sk-` regex does NOT cannibalize Anthropic keys (the `sk-ant-` rule
runs first, so it should be fine, but pin it).

### CR-05: `POST /api/chat` SSE error handler echoes raw exception text to clients

**File:** `backend/app/api/routes/routes.py:91-98`
**Issue:**

```python
except Exception as e:
    error_event = StreamEvent(
        chunk=f"An error occurred: {str(e)}",
        session_id=request.session_id,
        type="content",
    )
    yield f"data: {error_event.model_dump_json()}\n\n"
```

`str(e)` on an arbitrary upstream exception (httpx error, langchain provider
error, pydantic validation error, OpenAI SDK error, …) frequently contains
internal URLs (`https://api.openai.com/v1/...`), file paths, and — in the
worst case — request payload values that the SDK echoes back into the error
message. There are documented OpenAI / Anthropic SDK paths where the
response body (which can include the partial system prompt for context) is
embedded in the exception message.

The api_key itself is wrapped as `SecretStr` by the time it reaches the
SDK, so its `repr()` is `**********`, but the surrounding context (model
ids, base_url, account IDs) leaks freely. This violates the principle of
least information disclosure for an authenticated-but-not-trusted endpoint.

**Fix:** Log the full exception server-side (the scrubber will redact any
key-shaped substrings) and emit a generic error to the client:

```python
except Exception:
    logger.exception("chat_stream failed for session %s", request.session_id)
    error_event = StreamEvent(
        chunk="Sorry, something went wrong. Please try again.",
        session_id=request.session_id,
        type="content",
    )
    yield f"data: {error_event.model_dump_json()}\n\n"
```

(Adopting `logger.exception` is consistent with the project's logging
direction; the existing `print(...)` in `api/main.py:71` should also move
to `logger.info`.)

## Warnings

### WR-01: `chat_stream` mutates history before the user message is committed, with broad-except dropping every error path

**File:** `backend/app/chat.py:165-296`
**Issue:** The history append at `chat.py:281` (`history.add_user_message(message)`)
runs only after the streaming loop completes successfully. If
`bound.astream(messages)` raises partway through (e.g., daemon crash,
context-window overflow, network reset), the user's message is silently
dropped from the conversation history but the SSE error event in the route
layer (`routes.py:91`) still claims the message was processed.

Worse, the second `bound.astream(messages_with_tools)` inside the tool-call
branch (`chat.py:268`) can also raise after the user's message and tool
result have already been streamed out — but again, `history.add_user_message`
is below the loop, so the user's message and the tool round-trip are never
recorded. Subsequent turns will reference a tool result the LLM "remembers"
but the history doesn't.

Also, `accumulated_content` is sometimes the empty string (legitimate when
the model emits only thinking tokens), and `history.add_ai_message("")`
unconditionally writes an empty assistant turn — corrupting history when
the next turn rebuilds the context.

**Fix:**

1. Wrap the streaming sections in a try/finally so the user message is
   committed to history when the stream begins, not when it cleanly ends.
2. Only call `history.add_ai_message(accumulated_content)` when
   `accumulated_content` is non-empty (or call
   `history.add_ai_message(accumulated_content or "[no response]")` so the
   history is structurally sound).
3. Surface stream-mid-failure to the route layer so the error path doesn't
   pretend success.

### WR-02: `_test_openai_key` / `_test_anthropic_key` treat HTTP 5xx as `provider_unreachable`, masking server errors as transient

**File:** `backend/app/api/routes/routes.py:407-466`
**Issue:** Both test handlers catch `httpx.HTTPStatusError` (raised by
`response.raise_for_status()` on any 4xx/5xx outside the explicit `401` /
`429` carve-outs) and return `PROVIDER_UNREACHABLE`. That maps to a 502
that says "Try again in a moment." But:

- A 403 from OpenAI (e.g., key valid but org doesn't allow this model) is
  not a transient unreachability; the user should see "Forbidden / check
  permissions."
- A 400 from Anthropic (e.g., model id typo) is a configuration mistake;
  showing "Try again in a moment." sends the user into an infinite retry
  loop.
- A 5xx from the provider IS a transient unreachability and the current
  copy is right for that case only.

The 200 fast-path also isn't checked — any 2xx response that isn't 200
(e.g., 204, 202) currently falls through to "ok", which is fine but
fragile.

**Fix:** Differentiate the status code arms explicitly before
`raise_for_status`:

```python
if response.status_code == 401:
    return ProbeError(error=INVALID_API_KEY, ...)
if 400 <= response.status_code < 500:
    return ProbeError(error=INVALID_API_KEY,
                      message=f"OpenAI rejected the request ({response.status_code}).",
                      hint="Check the model id / key permissions.")
if response.status_code >= 500:
    return ProbeError(error=PROVIDER_UNREACHABLE, ...)
```

Drop the bare `raise_for_status()` since the explicit branches now cover
every HTTP outcome.

### WR-03: `refresh_providers` reports `provider_unreachable` for any empty model list, including legitimate "daemon up but no models loaded"

**File:** `backend/app/api/routes/routes.py:381-397`
**Issue:**

```python
models = cache.get(name, [])
available = bool(models)
error = None if available else "provider_unreachable"
```

`cache[name]` becomes `[]` in two distinct cases:

1. The daemon was unreachable and `factory.refresh_local_models()` returned
   `None`, which the caller normalised to `[]` (`routes.py:316`).
2. The daemon was reachable, returned 200, but the user has no models pulled
   yet (Ollama freshly installed, LM Studio with no models loaded).

Case (2) is reported as `error="provider_unreachable"` — a misleading wire
signal. The frontend `useProviderRefresh` hook will pop the F1 error banner
("Can't reach the daemon") when actually the daemon is fine and the user
just needs to run `ollama pull qwen3:4b`. The Sidebar / settings page UX
will direct the user to the wrong remediation.

**Fix:** Track the unreachable case explicitly. Either:

- Have `factory.refresh_local_models()` return a tuple
  `(models: list[str], reachable: bool)` per provider, OR
- Keep `None` as the sentinel for unreachable in `cache_timestamps` /
  the cache itself, distinct from the empty list.

Then in the route:

```python
if cache_entry is None:
    error = "provider_unreachable"
    available = False
elif len(cache_entry) == 0:
    error = None    # daemon up, no models — frontend can show "Run `ollama pull …`"
    available = False
else:
    error = None
    available = True
```

### WR-04: `get_providers` lazy-load triggers a daemon probe on every request when at least one provider's cache entry is empty due to unreachability

**File:** `backend/app/api/routes/routes.py:312-317`
**Issue:** The lazy-load condition is `name not in cache`. The first call
populates `cache["ollama"] = []` and `cache["lmstudio"] = []` even when
both daemons were unreachable. From the second call onward, the
"`name not in cache`" check is False so no further refresh runs — that's
correct. But the comment claims "Subsequent calls hit the cache regardless
of TTL" which is mis-leading: the explicit `/refresh` endpoint owns the
re-discovery cadence, and the lazy load doesn't respect TTL even on a stale
entry. If a user starts the backend with Ollama down, then starts Ollama,
they will see `available=False` on `GET /api/providers` until they hit
`/refresh` manually — an unobvious step.

This isn't a security issue, but a UX trap that pairs with WR-03: the
"daemon up, no models" reading is conflated with the unreachable reading,
so the user doesn't get the right hint either way.

**Fix:** Either make `GET /api/providers` honour the TTL (cheap — one extra
arithmetic compare), or document the manual-refresh requirement in the UI
copy.

### WR-07: `ChatService` injects the flight client a second time, masking missing-injection bugs

**File:** `backend/app/api/main.py:50`, `backend/app/chat.py:56`
**Issue:** Lifespan injects `search_flights._flight_client = flight_client`,
then `ChatService.__init__` does the same. Whichever runs second wins. If

**Fix:** Pick one location. The lifespan is the canonical owner; remove
line 56 in `chat.py` (it's an inheritance from the 4.2 service shape and
no longer needed now that the lifespan does it).

### WR-08: Module-level `from app.config import settings` couples routes to a separate `Settings()` instance from the lifespan

**File:** `backend/app/api/routes/routes.py:13`,
`backend/app/api/main.py:41`,
`backend/app/config.py:128`
**Issue:** Two `Settings()` instances live in the process: the
module-level one in `app.config` (imported by routes) and the local one in
`lifespan` (passed into `LLMProviderFactory`). The integration test
`test_session_create_returns_400_when_cloud_key_missing` already documents
this: it has to monkeypatch BOTH the route-side `settings.openai_api_key`
AND `factory._settings.openai_api_key` to make a single behavioural test
pass.

This is fragile and invites subtle bugs whenever a setting is read in two
places (e.g., a future feature reads `settings.foo` from a route AND from
a provider; updating one but not the other yields inconsistent runtime
behaviour). No security exposure today, but high refactor risk.

**Fix:** Store the single `Settings` instance on `app.state.settings` in
the lifespan, expose a `get_settings()` dependency, and have routes pull
from there instead of importing the module-level singleton. Delete the
module-level instance once all callers migrate.

### WR-09: `LMStudioProvider.list_models` `payload.get("data", [])` does not guard against a daemon returning a non-dict payload

**File:** `backend/app/llm/providers/lmstudio.py:136-142`
**Issue:** When the daemon is reachable but returns a non-JSON-object body
(e.g., a JSON array, a string, `null`), `payload.get(...)` raises
`AttributeError`. The `httpx.HTTPStatusError` / `ConnectError` /
`TimeoutException` in `validate_config` won't catch
`AttributeError`, so the call would surface as a 500 to the route layer.

The Ollama variant has the same shape (`payload.get("models", [])`).

**Fix:** Guard:

```python
payload = response.json()
if not isinstance(payload, dict):
    return []
data = payload.get("data", [])
if not isinstance(data, list):
    return []
```

Apply the same pattern to `OllamaProvider.list_models`.

### IN-01: `_resolve_allowed_cloud_models` discards the `bool` return-type case from `models["available"]`

**File:** `backend/app/api/routes/routes.py:116-140`
**Issue:** The signature is
`curated: dict[str, dict[str, list[str] | bool]]` and the function pulls
`curated[provider]["models"]`. The type hint `list[str] | bool` allows
`models` to legitimately be a `bool` here, in which case
`isinstance(models, list)` is False and the function returns `None`,
which the caller treats as "no whitelist enforced". The provider/model
combo would be allowed by the route. Today `Settings.get_available_providers`
puts `bool` only in `available` and `list[str]` only in `models`, so this
is theoretical, but the typing leaves the door open.

**Fix:** Tighten the inner dict shape (e.g., `TypedDict`) so `models` is
typed `list[str]` and `available` is typed `bool`, removing the runtime
isinstance check.

### IN-02: `provider_models_cache` and `provider_models_cache_timestamps` are typed as untyped dicts on `app.state`

**File:** `backend/app/api/main.py:64-65`
**Issue:** `app.state.provider_models_cache = {}` makes the type
`dict[Any, Any]`. The route hands re-narrows them with annotations:

```python
cache: dict[str, list[str]] = request.app.state.provider_models_cache
```

— but a future maintainer can stash `cache["ollama"] = None` (e.g. for an
unreachable signal) and the type checker stays silent. Combined with WR-03,
this is the kind of place where intent drifts.

**Fix:** Promote the cache to a small dataclass or a `TypedDict` and stash
that on `app.state` with an explicit annotation.

### IN-03: SSE `error` event is consumed by the frontend but the backend never emits one

**File:** `frontend/src/hooks/useChat.ts:283-290`,
`backend/app/api/routes/routes.py:72-98`
**Issue:** The frontend handles `event.type === 'error'` in
`readSSEStream`, but the backend chat handler never emits a
`type: "error"` StreamEvent — both error paths emit `type: "content"`.
The `'error'` arm in the frontend is dead code in practice. (Or, if the
intent was for the backend to emit `error` events, then CR-05's leak path
also defeats that intent.)

**Fix:** Either align the backend to emit `type: "error"` on internal
failures (and update the StreamEvent Literal to allow `"error"`), or drop
the dead frontend arm. Pick one.

### IN-04: `loadProviderSettings` rewrites localStorage on every call, even when the loaded shape is already complete

**File:** `frontend/src/lib/providerSettings.ts:93-105`
**Issue:** The migration block `localStorage.setItem(...)` always runs,
even when the parsed shape is byte-identical to `merged`. For users who
sit on `/settings/providers` and click around (each page mount calls
`loadProviderSettings`), every visit triggers a `setItem` write, which is
synchronous on the main thread. Cheap on its own; not free if storage is
constrained or if a `storage` event listener watches the key (the user's
other tabs would receive a meaningless storage event on every navigation).

**Fix:** Compare `JSON.stringify(merged) !== raw` before writing, so the
write only fires when an actual back-fill happens.

### IN-05: Settings page falls back to silent failure when `GET /api/providers` returns a non-2xx

**File:** `frontend/src/pages/SettingsProviders.tsx:60-94`
**Issue:** The `.then((response) => ...)` catches `!response.ok` by returning
null and short-circuiting. The user sees the locally cached models from
`localStorage` and no banner indicating "we tried to refresh and failed."
Combined with WR-03, a daemon transition (running → not running between
the cached snapshot and the fresh probe) is invisible.

**Fix:** Surface a soft banner on probe failure ("Couldn't refresh model
list — using cached data."). The `SelectorErrorBanner` component is
already wired in `ProviderCard` for the `Refresh models` button; reuse it
at the page level.
