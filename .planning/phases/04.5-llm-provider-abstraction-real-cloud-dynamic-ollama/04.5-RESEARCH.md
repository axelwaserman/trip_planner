# Phase 4.5: LLM Provider Abstraction (real cloud + dynamic Ollama) — Research

**Researched:** 2026-05-16
**Domain:** LangChain provider abstraction, async HTTP discovery, FastAPI per-session DI, OpenAI/Anthropic/Ollama/LM Studio integrations
**Confidence:** HIGH (stack), HIGH (Ollama wire format — verified live), MEDIUM (LM Studio — daemon not running locally to verify), HIGH (LangChain provider signatures — inspected against installed packages)

## Summary

Phase 4.5 replaces the singleton `BaseChatModel` built at app startup with a Protocol-based provider abstraction that is constructed per-session. Four implementations land — `OllamaProvider`, `LMStudioProvider`, `OpenAIProvider`, `AnthropicProvider` — built on top of the official LangChain integration packages (`langchain-ollama`, `langchain-openai`, `langchain-anthropic`). All three integration packages expose the LangChain `BaseChatModel` surface (`ainvoke`, `astream`, `bind_tools`) verified by direct inspection of the installed wheels. LM Studio piggy-backs on `ChatOpenAI` with a custom `base_url` and a sentinel `api_key="lm-studio"` since LM Studio's REST surface is OpenAI-compatible.

The Protocol surface mirrors today's `BaseChatModel` consumption in `chat.py::chat_stream` (line 117 `self.llm.astream(messages)` and line 142 `chunk.tool_calls`). Critically, `bind_tools` does NOT return a `BaseChatModel` — it returns `Runnable[LanguageModelInput, AIMessage]` — so the Protocol must distinguish "raw provider" (has `bind_tools`) from "bound provider" (has only `ainvoke`/`astream`). The cleanest shape is two members: `bind_tools(...) -> BoundProvider` and a `BoundProvider` Protocol exposing `ainvoke` + `astream`.

`validate_config()` migrates the entire 4.2 probe surface onto the Protocol. The existing `ProbeError` Pydantic model and `ProbeErrorCode` `StrEnum` (`backend/app/services/provider_probe.py:16`) are the wire contract that frontend's `mapProbeError` (`frontend/src/lib/providerErrors.ts:39`) consumes — they relocate to `app/llm/errors.py` unchanged, gaining one new code (`INVALID_API_KEY`) for the opt-in "Test connection" button.

Cloud acceptance tests use `pytest.mark.skipif(not os.getenv("OPENAI_API_KEY"), ...)` and live in `tests/integration/` (not `e2e/`) — `tests/e2e/` is reserved for full-stack auth + travel-API flows per `backend/tests/e2e/README.md`. The skipif decorator composes with the existing `pytest.mark.integration` marker.

**Primary recommendation:** Land four provider classes under `backend/app/llm/providers/`, a `LLMProviderFactory` that builds them from session-scoped config, a relocated `app/llm/errors.py` (carrying `ProbeError` + `ProbeErrorCode`), and a per-session bound-provider stash on `ChatService._sessions[session_id].bound_provider`. Wire `validate_config()` into `POST /api/chat/session` exactly where `probe_provider()` lives today; delete the old `services/provider_probe.py`. Cloud `validate_config` does env/payload-key presence only — no outbound call by default — preserving today's session-create UX.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Provider Lifecycle & DI Shape (D-01–D-03):**
- `ChatService` stays a singleton; bound provider object built at `create_session` and stored on session metadata.
- `create_session(provider, model, base_url=None, api_key=None)` calls `LLMProviderFactory.build(...)`, runs `provider.validate_config()`, calls `provider.bind_tools([search_flights])`, stores bound provider on per-session state. `bind_tools()` runs once per session.
- Provider/model is locked at session-create — no mid-chat switching. Switching = new session.
- Lifespan no longer instantiates a default LLM. `app.state.llm_factory = LLMProviderFactory(settings)` replaces the `init_chat_model(...)` block.
- `ChatService` is constructed with the factory, not a `BaseChatModel`. The `MockFlightAPIClient` injection into `search_flights._flight_client` stays.

**Discovery & Refresh (D-04–D-07):**
- Dynamic model discovery for local providers only (Ollama, LM Studio); cloud providers keep curated model lists.
- `OllamaProvider.list_models(base_url)` hits `GET /api/tags`. `LMStudioProvider.list_models(base_url)` hits `GET /v1/models`.
- Discovery cache is in-memory on `app.state`, populated on first `GET /api/providers` after restart, invalidated only by Refresh button. No TTL.
- Single global `POST /api/providers/refresh` button; backend re-discovers all available local providers in parallel (`asyncio.gather`).
- `list_models` lives on the `LLMProvider` Protocol, not on the probe service. Each provider class owns its discovery.

**API Keys (D-08–D-11):**
- Session-payload key wins; env-var key is the fallback. `LLMProviderFactory.build(provider, model, api_key=payload_key)` uses `payload_key or settings.{provider}_api_key`.
- API keys captured in `POST /api/chat/session` payload, held on session metadata in process memory, never logged, never persisted to disk. Dies with the session.
- Logs scrub fields named `api_key` / `*_api_key` and string patterns `sk-...` / `sk-ant-...`. Minimal scrubber lands in 4.5; `structlog`-based scrubbing is Phase 8.
- Backend-stored encrypted API keys deferred to Phase 5 (PG + KEK derivation).

**`validate_config` & Test Connection (D-12–D-14):**
- `LLMProvider.validate_config()` IS the probe — `services/provider_probe.py` migrates onto the Protocol.
- `ProbeError` and `ProbeErrorCode` types stay (existing wire contract); they relocate to `app/llm/errors.py`.
- Default `validate_config()` for Ollama/LMStudio: liveness probe (`/api/tags` or `/v1/models`) + selected-model presence check. Returns `provider_unreachable` / `model_not_installed`.
- Default `validate_config()` for OpenAI/Anthropic: key presence only (env or payload). Returns `missing_api_key` if neither source has a key. **No outbound API call by default** — preserves today's session-create UX.
- Live cloud key validation is opt-in via `POST /api/providers/{provider}/test`. OpenAI: `GET /v1/models` (cheap, no token cost). Anthropic: `POST /v1/messages` with `max_tokens: 1`. New `ProbeErrorCode.INVALID_API_KEY` value added.

**LM Studio Integration (D-15–D-18):**
- `LMStudioProvider` is a first-class, distinct provider class. Default `base_url=http://localhost:1234/v1`.
- Internal implementation may delegate to `langchain-openai`'s `ChatOpenAI` with custom `base_url` and sentinel `api_key="lm-studio"`. Researcher confirmed below.
- LM Studio requires no API key in v1. Local trust model.
- Discovery via `GET /v1/models`. `validate_config()` checks `/v1/models` for liveness + selected model id.

**Frontend & Backend route shape (D-19–D-28):** see CONTEXT.md verbatim. The session-create payload extends to `{provider, model, base_url, api_key}`; new endpoints `POST /api/providers/refresh`, `POST /api/providers/{provider}/test`, `GET /api/chat/sessions`. New Settings field: `lmstudio_base_url: str = "http://localhost:1234/v1"`.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| LLM Protocol definition | Backend (app/llm/) | — | Pure backend type contract; no client involvement. |
| Per-session provider construction | Backend (ChatService) | — | Provider object built at `create_session()` from session-scoped config; cannot live on the client. |
| Cloud API key acceptance | Backend (POST /api/chat/session payload) | Frontend (localStorage `provider_settings`) | Frontend owns the form + storage; backend owns the routing of payload→factory and the never-log invariant. |
| Dynamic model discovery (Ollama / LM Studio) | Backend (provider class) | Backend (cache on `app.state`) | Backend hits localhost daemon over httpx; cache is a backend concern (not localStorage) so the data is reused across sessions in the same process. |
| Discovery cache invalidation | Backend (POST /api/providers/refresh) | Frontend (Refresh button click) | Endpoint is backend; trigger is a UI button. |
| API key validation (live) | Backend (POST /api/providers/{p}/test) | Frontend ("Test connection" button) | Backend makes the cheapest possible outbound call; UI displays success/error. |
| Session-create error surface | Backend (HTTPException with structured detail) | Frontend (`SelectorErrorBanner`) | Backend emits the `ProbeError` JSON body; frontend's `mapProbeError` translates to `ProviderErrorView` (already in place from 4.2). |
| Sidebar chat list | Backend (GET /api/chat/sessions) | Frontend (Sidebar component) | Backend reads `ChatService._histories.keys()`. |
| Provider/model selection UI | Frontend (`/settings/providers` page) | Frontend (localStorage write) | Pure frontend; backend never persists user preferences in 4.5. |

**Why this matters for the planner:** The `bind_tools([search_flights])` callsite must remain server-side (the tool is server-side code), and the Protocol's `bind_tools` member is consumed exactly once per session inside `ChatService.create_session`. Misplacing it in lifespan (today's pattern) is the bug 4.5 fixes.

### Pattern 1: Two-Protocol Shape (raw + bound)

**What:** Distinguish the "configurable provider" (has `bind_tools`) from the "bound provider" (has `ainvoke` / `astream`).
**When to use:** Always — `bind_tools()` returns a `Runnable[LanguageModelInput, AIMessage]`, NOT a `BaseChatModel`. The Runnable does not expose `bind_tools` for a second binding pass.
**Why:** Type safety; eliminates the temptation to call `bind_tools` twice on a session.

```python
# Source: app/llm/protocol.py (proposed)
# Verified against langchain_core.language_models.chat_models.BaseChatModel:
#   bind_tools(...) -> Runnable[LanguageModelInput, AIMessage]
#   astream(input, config=None, *, stop=None, **kw) -> AsyncIterator[AIMessageChunk]
#   ainvoke(input, config=None, *, stop=None, **kw) -> AIMessage

from collections.abc import AsyncIterator, Sequence
from typing import Any, Protocol, runtime_checkable

from langchain_core.messages import AIMessage, AIMessageChunk, BaseMessage
from langchain_core.tools import BaseTool

from app.llm.errors import ProbeError


@runtime_checkable
class BoundProvider(Protocol):
    """A provider with tools already bound. Used by ChatService.chat_stream."""

    async def ainvoke(self, input: list[BaseMessage], **kwargs: Any) -> AIMessage: ...

    def astream(self, input: list[BaseMessage], **kwargs: Any) -> AsyncIterator[AIMessageChunk]: ...


@runtime_checkable
class LLMProvider(Protocol):
    """Per-session provider built by LLMProviderFactory."""

    def get_provider_name(self) -> str: ...

    async def validate_config(self) -> ProbeError | None:
        """Cheap config check. Returns None on success.

        Default behavior:
        - Local providers: HTTP liveness probe + selected-model presence.
        - Cloud providers: env/payload key presence only (no outbound call).
        """
        ...

    def bind_tools(self, tools: Sequence[BaseTool]) -> BoundProvider:
        """Bind tools and return a session-bound provider."""
        ...

    async def list_models(self) -> list[str]:
        """Return discovered model ids.

        Local providers: hit the daemon. Cloud providers: return curated list.
        """
        ...
```

### Pattern 2: Factory Builds from Session-Scoped Config

```python
# Source: app/llm/factory.py (proposed)

from dataclasses import dataclass

from app.config import Settings
from app.llm.protocol import LLMProvider
from app.llm.providers.anthropic import AnthropicProvider
from app.llm.providers.lmstudio import LMStudioProvider
from app.llm.providers.ollama import OllamaProvider
from app.llm.providers.openai import OpenAIProvider


@dataclass(frozen=True)
class SessionLLMConfig:
    """Per-session LLM configuration, assembled from request payload + Settings fallbacks."""

    provider: str
    model: str
    base_url: str | None  # local providers only
    api_key: str | None   # cloud providers only


class LLMProviderFactory:
    """Per-app factory; builds session-scoped providers."""

    def __init__(self, settings: Settings) -> None:
        self._settings = settings

    def build(self, config: SessionLLMConfig) -> LLMProvider:
        match config.provider:
            case "ollama":
                return OllamaProvider(
                    model=config.model,
                    base_url=config.base_url or self._settings.ollama_base_url,
                    probe_timeout_seconds=self._settings.provider_probe_timeout_seconds,
                )
            case "lmstudio":
                return LMStudioProvider(
                    model=config.model,
                    base_url=config.base_url or self._settings.lmstudio_base_url,
                    probe_timeout_seconds=self._settings.provider_probe_timeout_seconds,
                )
            case "openai":
                return OpenAIProvider(
                    model=config.model,
                    api_key=config.api_key or self._settings.openai_api_key,
                )
            case "anthropic":
                return AnthropicProvider(
                    model=config.model,
                    api_key=config.api_key or self._settings.anthropic_api_key,
                )
            case _:
                raise ValueError(f"Unknown provider: {config.provider}")
```

### Pattern 3: Per-Session Bound Provider Storage on ChatService

```python
# Source: app/chat.py (proposed signature change)

class ChatService:
    def __init__(self, flight_client: FlightAPIClient, factory: LLMProviderFactory) -> None:
        self._factory = factory
        self._histories: dict[str, InMemoryChatMessageHistory] = {}
        self._metadata: dict[str, dict[str, str]] = {}
        self._bound_providers: dict[str, BoundProvider] = {}  # NEW
        self._last_activity: dict[str, float] = {}
        search_flights._flight_client = flight_client

    async def create_session(self, config: SessionLLMConfig) -> tuple[str, ProbeError | None]:
        provider = self._factory.build(config)
        if (probe_error := await provider.validate_config()) is not None:
            return "", probe_error
        bound = provider.bind_tools([search_flights])
        session_id = str(uuid.uuid4())
        self._histories[session_id] = InMemoryChatMessageHistory()
```

### Anti-Patterns to Avoid

- **Don't reach for a `BaseChatModel` type alias on the Protocol.** The Protocol's job is to wrap the LangChain surface, not re-export it. Cross-import only via `BoundProvider`.
- **Don't store the raw `LLMProvider` per session — only the `BoundProvider`.** `bind_tools()` runs once at session-create, never again. Keeping the raw provider invites accidental double-binding.
- **Don't pass `api_key` as a query param or path param to any new endpoint.** Keys travel only in JSON request bodies.
- **Don't smear `validate_config` and `list_models` across two layers.** Both belong on the provider class. The 4.2 probe-as-free-function pattern is the trap to avoid (CONTEXT.md §"Anti-patterns").
- **Don't gate the live cloud test on every settings-page save.** That re-introduces the surprise-billing risk D-14 explicitly rejected. Live test = explicit "Test connection" button only.
- **Don't hard-code `qwen3:4b` defaults in the new code paths.** Today's `Settings.default_model` exists; the factory uses Settings only as fallback for env-supplied keys, not for model names. Per-session config is the source of truth.

## Common Pitfalls

### Pitfall 1: `bind_tools` Returns a Runnable, Not a `BaseChatModel`

**What goes wrong:** Code expects to call `provider.bind_tools(...)` and then later call `bound.bind_tools(...)` again, or to introspect `bound.model_name`.
**Why it happens:** `BaseChatModel.bind_tools` returns `Runnable[LanguageModelInput, AIMessage]` (verified against installed `langchain-core` 1.x). The Runnable has `ainvoke`/`astream` but is not a `BaseChatModel`.
**How to avoid:** Two Protocols (`LLMProvider` for raw, `BoundProvider` for post-bind) — see [Pattern 1](#pattern-1-two-protocol-shape-raw--bound).
**Warning signs:** `mypy` errors of the form `"Runnable" has no attribute "bind_tools"`; runtime AttributeError on `.model_name`.

### Pitfall 2: ChatAnthropic Requires a Non-Empty `api_key` at Construction

**What goes wrong:** Constructing `ChatAnthropic(model=..., api_key=None)` raises a Pydantic validation error before any code path can probe it.
**Why it happens:** Verified against `langchain-anthropic` 1.4.3: `anthropic_api_key: pydantic.types.SecretStr` is required (not Optional). ChatOpenAI is more lenient (`SecretStr | None | Callable`).
**How to avoid:** `validate_config()` for AnthropicProvider must check `api_key is not None` BEFORE `ChatAnthropic(...)` is constructed. The provider class can store the key separately and only instantiate `ChatAnthropic` lazily when `bind_tools()` is called (after `validate_config` has passed).
**Warning signs:** `pydantic.ValidationError: 1 validation error for ChatAnthropic` raised from inside `factory.build(...)` instead of from `validate_config()`.

### Pitfall 3: LM Studio Requires a Non-Empty `api_key` Even When Not Using Auth

**What goes wrong:** `ChatOpenAI(base_url="http://localhost:1234/v1", api_key=None)` raises in the underlying `openai` SDK validator.
**Why it happens:** The OpenAI SDK requires the `api_key` field to be a non-empty string for client construction, even if the local server doesn't enforce it. CONTEXT.md D-16 calls this out explicitly.
**How to avoid:** Pass a sentinel value: `api_key="lm-studio"`. The string is never sent to a real OpenAI endpoint because `base_url` overrides the destination.
**Warning signs:** `openai.OpenAIError: The api_key client option must be set...`

### Pitfall 4: Ollama Response Shape Variance Between Versions

**What goes wrong:** The probe matches on `entry["name"]` only; older or newer Ollama versions add or remove the `name` key.
**Why it happens:** The 4.2 probe already handles this — it matches on both `name` AND `model` keys (`backend/app/services/provider_probe.py:80`). Verified live against running Ollama 0.23.4: both fields present and identical (`{"name":"qwen3:4b","model":"qwen3:4b",...}`).
**How to avoid:** Preserve the existing `{entry.get("name") for ...} | {entry.get("model") for ...}` defensive pattern when migrating to `OllamaProvider.validate_config()`.
**Warning signs:** `model_not_installed` returned even though `ollama list` shows the model — indicates the response shape changed and only one of the two keys is populated.

### Pitfall 5: API Keys Leaking Through `repr()` / Stack Traces

**What goes wrong:** A `ChatAnthropic` instance is logged via `repr()` in an exception handler; the full key appears in logs.
**Why it happens:** Pydantic's `SecretStr` masks the value in `repr` and `str` (returns `'**********'`), but third-party loggers may call `model_dump()` (which exposes `SecretStr` fields unless `mode='json'` is used) or pickle the object.
**How to avoid:** (1) Never log the provider object itself, only `provider.get_provider_name()`. (2) Add a global logging filter that regex-redacts `sk-[A-Za-z0-9]+` and `sk-ant-[A-Za-z0-9-]+` (D-10). (3) When dumping config for diagnostics, build a sanitized dict explicitly — never `model_dump()`.
**Warning signs:** Any log line containing `sk-` should be a build-time CI check (rgrep over recent log fixtures) before merge.

### Pitfall 6: Unbounded Discovery on First Cold Start

**What goes wrong:** First `GET /api/providers` after restart synchronously waits on Ollama + LM Studio probes; if both daemons are slow or unreachable, the user sees a 30-second hang.
**Why it happens:** D-05 says the cache is populated lazily on first read. Without a per-probe timeout, a TCP-level black hole on `localhost:11434` blocks the whole request.
**How to avoid:** Reuse `Settings.provider_probe_timeout_seconds` (1.5s default — already on Settings). `asyncio.gather(*probe_tasks, return_exceptions=True)` ensures one slow daemon doesn't block the other. Mark unreachable providers `available: False` in the response, leaving their `models` list empty — the frontend's "Refresh" button is the recovery affordance.
**Warning signs:** `GET /api/providers` p95 latency > 2× `provider_probe_timeout_seconds`.

### Pitfall 7: Reasoning Tokens Are Provider-Specific

**What goes wrong:** Code assumes `chunk.additional_kwargs["reasoning_content"]` is the universal reasoning channel; OpenAI o1/o3 expose reasoning differently (or not at all over the chat completions API), Anthropic expose `thinking` as a separate event type.
**Why it happens:** Today's `chat.py:121` reads `chunk.additional_kwargs.get("reasoning_content")` — this works for `ChatOllama(reasoning=True)` but is not portable to OpenAI/Anthropic.
**How to avoid:** Treat reasoning as an **Ollama-only** concern in 4.5. The Protocol does NOT abstract reasoning; the existing `chunk.additional_kwargs.get("reasoning_content")` path simply yields nothing for cloud providers (which is correct — they don't emit it on this attribute). Phase 6's PydanticAI migration is the right place to revisit a unified reasoning channel.
**Warning signs:** Cloud-provider chats show no thinking events — that's expected. If the user expects thinking on cloud providers, surface that as a feature deferred to Phase 6.

### Known Threat Patterns for Per-Session API Key Acceptance

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| API key in URL / query string / path | Information Disclosure | Keys travel only in JSON request bodies (D-09); validate that no new endpoint accepts keys in path/query. |
| API key leaking through `repr()` / `model_dump()` / stack trace logs | Information Disclosure | Pydantic `SecretStr` for in-memory storage where possible; regex scrubber on stdout/stderr; no `model_dump()` on provider objects in error handlers. |
| Cross-session key reuse via shared cache | Tampering | Bound provider + key are stored in `ChatService._bound_providers[session_id]` — keyed by session id; not in a global. Verify by adding a test that two sessions with different keys do not see each other's bound provider. |
| Frontend localStorage XSS exfiltration | Information Disclosure | XSS hardening (CSP + `rehype-sanitize`) is Phase 8. v1 accepts the localStorage trust model (per CONCERNS.md). Surface this in any user-facing docs that warn about pasting cloud keys on shared machines. |
| Server-Side Request Forgery via `base_url` | Tampering / Server-Side Request Forgery | The `base_url` in the session payload is user-controlled. Currently nothing prevents `base_url=http://internal-metadata-service/`. **Recommended:** validate `base_url` matches one of `localhost`, `127.0.0.1`, `host.docker.internal` (for Phase 5 compose), or any host explicitly enabled via a `Settings.lmstudio_allowed_hosts` allowlist. v1 default = localhost-only. Document this constraint in the validation error message. |
| `provider` parameter injection (e.g., `provider="../../etc/passwd"`) | Tampering | The factory uses `match config.provider` against a fixed `Literal` set; reject unknown providers with a 400 (already the existing 4.2 path). |
| Slow-loris on `/api/providers/refresh` | Denial of Service | `Settings.provider_probe_timeout_seconds` (1.5s) caps each underlying probe. Refresh runs `asyncio.gather(*tasks, return_exceptions=True)` so one slow probe doesn't block the response. |
| Rate-abuse on `/api/providers/{provider}/test` | Denial of Service | No rate limit in v1 (ADR-009). Authenticated route mitigates the worst (no public surface). |

### Specific Pydantic validators to add

On `SessionCreateRequest`:

```python
from pydantic import BaseModel, Field, field_validator
from urllib.parse import urlparse

class SessionCreateRequest(BaseModel):
    provider: str | None = Field(default=None)
    model: str | None = Field(default=None)
    base_url: str | None = Field(default=None, description="Local providers only; ignored for cloud")
    api_key: str | None = Field(default=None, description="Cloud providers only; ignored for local")

    @field_validator("api_key")
    @classmethod
    def _strip_and_bound_api_key(cls, v: str | None) -> str | None:
        if v is None:
            return None
        s = v.strip()
        if not s:
            return None
        if len(s) > 256:
            raise ValueError("api_key exceeds maximum length (256 chars)")
        return s

    @field_validator("base_url")
    @classmethod
    def _validate_base_url(cls, v: str | None) -> str | None:
        if v is None:
            return None
        parsed = urlparse(v)
        if parsed.scheme not in ("http", "https"):
            raise ValueError("base_url must be http or https")
        if parsed.hostname not in ("localhost", "127.0.0.1", "host.docker.internal"):
            raise ValueError(
                "base_url host must be localhost, 127.0.0.1, or host.docker.internal in v1"
            )
        return v
```

## Phase 6 Forward-Compat Note

Phase 6 swaps LangChain for PydanticAI. PydanticAI is `Agent`-shaped: tools are registered against an Agent instance, and the Agent owns both the model and the tool list. There is no `bind_tools` member; the equivalent is `Agent(model, tools=[...])` or `@agent.tool` decoration.

**To minimise rework, the 4.5 Protocol should:**
1. Keep `LLMProvider` and `BoundProvider` as separate Protocols (already recommended). When PydanticAI lands, `LLMProvider.bind_tools` retires and `BoundProvider` becomes the Agent-equivalent.
2. Keep `validate_config` and `list_models` on the provider, NOT on the bound surface — these survive the migration unchanged.
3. Keep `get_provider_name` — survives unchanged.
4. NOT promote `BaseChatModel`/`Runnable` types into the Protocol's public signatures. Use `BaseMessage`/`AIMessage`/`AIMessageChunk` from `langchain-core.messages` only inside the `BoundProvider` Protocol, and accept they will be replaced by PydanticAI's `ModelMessage`-style types in Phase 6.

**Explicit acknowledgement (per CONTEXT.md):** `bind_tools` retires from the Protocol in Phase 6. Do NOT propose an Agent-shaped Protocol now (rejected — would be premature gold-plating). Phase 4.5 mirrors LangChain's surface; Phase 6 absorbs the rework.

## Open Questions (RESOLVED)

1. **Should `langchain` (umbrella) be removed in 4.5 or deferred to Phase 6?**
   - What we know: `init_chat_model` is the only `langchain` (umbrella) symbol used in production code (`api/main.py:8,37`). After 4.5, it's no longer used.
   - What's unclear: Whether there are any `langchain.*` imports lurking elsewhere; the cost of running a grep + uv-tree audit vs. the benefit of slimming deps in 4.5.
   - **RESOLVED:** Defer to Phase 6 (when LangChain is removed wholesale). 4.5 plan does NOT remove `langchain` from `pyproject.toml`. Avoids dependency churn risk in the same phase that adds two new packages.

2. **Should the cloud test endpoint use `respx` for clean httpx mocking, or stay on monkeypatch?**
   - What we know: 4.2 used monkeypatch successfully. `respx` is more ergonomic for asserting request shape (URL, headers, body).
   - What's unclear: Whether the test cases need request-shape assertions strong enough to justify a new dep.
   - **RESOLVED:** Stay with monkeypatch. Tests assert response handling, not request shape — monkeypatch is sufficient.

3. **Should `ChatService` become async-construction (`async def create_session`) or keep sync?**
   - What we know: Today's `create_session` is synchronous. Adding `await provider.validate_config()` makes it async.
   - What's unclear: Whether the route layer's existing `await` pattern accommodates this (yes — the current 4.2 path already does `await probe_provider(...)` in the route, then calls a sync `chat_service.create_session()`).
   - **RESOLVED:** Make `ChatService.create_session` async (`async def`). Move `await provider.validate_config()` and `provider.bind_tools(...)` inside it so the route layer just `await chat_service.create_session(config)`. Cleaner contract, single transactional unit.

4. **Should `validate_config` for the cloud providers attempt a tiny outbound call when the user explicitly clicks "Test connection", or always go through the separate `/test` endpoint?**
   - What we know: D-13 keeps `validate_config` cheap (key presence only). D-14 routes the live check through `POST /api/providers/{p}/test`.
   - What's unclear: None — the answer is the explicit `/test` endpoint, which I've already enumerated. No ambiguity.
   - **RESOLVED:** As CONTEXT.md specifies — keep the two paths separate. `validate_config` is the cheap key-presence check; `POST /api/providers/{provider}/test` is the live cloud probe.

5. **Does the Sidebar's "Recent chats" list need to filter to the authenticated user's sessions?**
   - What we know: `ChatService._histories` is keyed by session id, not by user id. There's no per-user partitioning today. With multi-user deployments, one user could see another user's session ids.
   - What's unclear: Whether v1 (single-user, demo-grade) makes this a real concern — `AUTH_USERS` typically has one admin.
   - **RESOLVED:** Plan adds a `_user_id` field to `ChatService._metadata[session_id]` set at create time, and `GET /api/chat/sessions` filters by `current_user.username`. Cheap to add now; awkward to retrofit at Phase 5 PG migration.
