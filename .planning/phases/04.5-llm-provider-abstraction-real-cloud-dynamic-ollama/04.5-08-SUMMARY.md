## Deviations from Plan

Three pre-UAT points + three post-UAT polish deviations.

### Pre-UAT (build-time / scope-locked)

1. **`ProviderCard` Model select is a plain `<select>`, not `Box as="select"`.** UI-SPEC §"ProviderCard" says "native `<select>` styled to match Chakra `<Input>`". The PLAN action says "use a hardcoded curated list per provider". Initial implementation used `Box as="select"` to keep theme tokens, but `tsc -b` strict mode rejected the polymorphic onChange typing. Switched to a plain `<select>` with inline-style CSS variables (`var(--chakra-colors-*)`) — same theme tokens, same visual result, types pass. Documented inline in the GREEN commit message.
2. **Status pill omits `Unreachable`.** UI-SPEC documents three states (Ready / Needs setup / Unreachable). The card derives status from the saved settings only; live probing is out of scope per the PLAN action ("Refresh button … Test connection button … underlying endpoints are OUT of orchestrator scope"). The Unreachable visual is rendered when a future plan wires in live probing. Today the pill switches between Ready and Needs setup — sufficient for the visible deliverable Plan 08 ships.
3. **Settings IconButton is in the chat header, not in a Sidebar.** The PLAN explicitly notes this: "Plan 08b removes this IconButton in favor of a single settings entry point via the Sidebar; it lives here in 08 only because 08 ships before Sidebar exists." This is the planner's documented direction, not a deviation.

### Post-UAT polish round 1 (commit `fc1e61b`)

The user surfaced three issues during the first manual UAT — all real, all addressed before sign-off:

4. **[Rule 1 — Bug] Model select didn't update after Base URL change.** The Model `useState` snapshotted `settings.ollama.models` at mount, so any parent-level change (e.g. a future Refresh, or a sibling card mutating settings) never reached the dropdown. Round-1 fix added a `useEffect` re-aligning local model state when upstream models change. Round-2 (#7 below) eliminated the dropdown entirely. **Files:** `frontend/src/components/ProviderCard.tsx`.
5. **[Rule 2 — UX gap, agreed with user] Badge clicked → settings page (redundant with the gear icon).** UI-SPEC §"ChatInterface modifications" mandated the navigation behavior. The UX-stronger pattern is a popover quick-switcher: badge opens a Chakra v3 `Menu.Root` listing Ready providers from saved settings; selecting one calls `useChat.handleProviderChange`. Footer item "Manage providers…" is the path to the full settings page; the gear IconButton stays as the second path. Re-reads settings on every open via an `onOpenChange` tick. **Files:** `frontend/src/components/ChatInterface.tsx`.
6. **[Rule 1 — Bug] Misleading helper copy "Stored in this browser only. Never sent to our server."** The api_key DOES travel to our backend over HTTPS at session-create time — that's how LangChain authenticates to the LLM API. Round-1 expanded the helper to spell out the session-start travel. Round-2 (#11 below) shortened it to a single sentence at user request. **Files:** `frontend/src/components/ProviderCard.tsx`, `frontend/src/pages/SettingsProviders.tsx`.

### Post-UAT polish round 2 (commit `b294425`)

After round-1 polish landed, the user surfaced five more issues during the second UAT round:

7. **[Rule 1 — Bug] Only one Ollama model showed up.** The settings page seeded `settings.ollama.models` from localStorage only; nobody ever populated the field, so the card rendered a single fallback. Fixed by fetching `GET /api/providers` on settings-page mount and merging `payload.ollama.models` into local state. Backend lazy-discovery hits the daemon's `/api/tags` on first call. **Files:** `frontend/src/pages/SettingsProviders.tsx`.
8. **[Rule 1 — Bug] Same bug in the chat-header popover.** Single Ollama row instead of one row per discovered model. Fixed by adding the same `GET /api/providers` fetch to `ChatInterface`, feeding the live list into a new `buildQuickSwitchOptions(liveOllamaModels)`. Falls back silently to saved settings if discovery fails. **Files:** `frontend/src/components/ChatInterface.tsx`.
9. **[Rule 2 — UX gap, agreed with user] Settings-page Model `<select>` didn't fit the page's purpose.** The settings page is for *configuring* a provider (URL/key); active-model selection happens in the chat-header popover. Replaced the dropdown with a read-only chip-list (`Wrap` of pill-shaped `Box` spans, mono font) under an "Available models" heading, plus a reminder underneath that the active model lives in the chat-header badge. **Files:** `frontend/src/components/ProviderCard.tsx`.
10. **[Rule 2 — Scope, agreed with user] OpenAI / Anthropic cards dropped from the settings page.** Without a real Test-connection probe (still deferred — the endpoint never landed), the user can't verify whether a typed key is valid before paying for a chat. Cards removed. The backend factory branches and the `ProviderSettings` schema entries for `openai` / `anthropic` are kept intact for forward compat — `useChat` still drives them; a future plan can re-enable the cards without touching the lib layer. **Files:** `frontend/src/pages/SettingsProviders.tsx`.
11. **[Rule 1 — Copy] Helper text shortened.** Round-1's "We never store your key on our servers. It travels to our backend only when starting a chat session, so the model can authenticate to {OpenAI|Anthropic}." was correct but verbose. User asked for the shorter "We never store your key on our servers." — same load-bearing claim, half the words. Same shortening applied to the settings-page intro paragraph. **Files:** `frontend/src/components/ProviderCard.tsx`, `frontend/src/pages/SettingsProviders.tsx`.

## Issues Encountered

1. **`getByLabelText(/API Key/i)` matched both the Field.Label and the IconButton aria-label "Show/Hide API key".** Caught at first `npm test -- ProviderCard` run — 4 of 8 tests failed with "found multiple elements matching". Fixed by switching to exact-match strings (`getByLabelText('API Key')`, `getByRole('button', { name: 'Show API key' })`) so the matcher disambiguates between the label and the toggle aria-label.
2. **`vi.spyOn(Storage.prototype, 'setItem')` returned 0 calls.** The repository's `frontend/src/test-setup.ts` defines `window.localStorage` as a plain object (not a `Storage` subclass), so prototype spies don't catch instance calls. Fixed by switching to `vi.spyOn(localStorage, 'setItem')` — spies on the shim instance directly.
3. **`Box as="select"` failed `tsc -b` strict typing.** Box's polymorphic `as` prop produces a type that doesn't include the `select`-specific HTMLSelectElement event types. Fixed by switching the Model select to a plain `<select>` with inline-style CSS variables (covered above in Deviations §1).
4. **`Box as="button" type="button"` failed `tsc -b` strict typing** — Box's polymorphic `as="button"` does not propagate the HTMLButtonElement `type` prop. Dropped the explicit `type` prop on the active-model badge; default-to-button-as-button under DOM behaviour.
